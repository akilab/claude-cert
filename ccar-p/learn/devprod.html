開発生産性と運用支援 配点 7%

チームへの Claude Code の展開、AI を使った開発の流れ、運用上の問題の解決を扱います。CCDV-F の Claude Code の知識を、組織の視点で使う分野です。

チームへのツールの展開

設定の層置く場所置くもの
組織管理者が配布する設定（managed settings）全員に強制する安全基準（禁止するコマンド、読ませないファイル、許可する MCP）
プロジェクトリポジトリの CLAUDE.md、共有の settings.jsonそのリポジトリの決まり、テストのコマンド、プロジェクト用の権限やフック
個人~/.claude/ の設定個人の好み
  • 安全基準は個人に任せず、組織の設定で一律に適用する。
  • カスタムコマンド・Skills・プラグインで、チームのやり方を共有する。
  • MCP サーバーは出どころと権限を確認し、許可したものだけを使えるようにする。

Claude Code の基本は CCDV-F の Claude Code のページ にまとめています。

AI を使った開発の流れ

  • 大きな変更をいきなり頼まず、計画 → 確認 → 小さく実装 → テスト → レビューを繰り返す。
  • テストを成功基準にすると、AI に任せられる範囲を広げやすい。
  • CI でヘッドレスモードを使い、レビューの補助や定型作業を自動化する。
  • AI が書いたコードもレビューする。セキュリティの観点は特に。

運用上の問題の解決

  1. 影響の把握：誰に、どれだけ、いつから。
  2. 再現条件の特定：request-id とトレースで、該当するリクエストを探す。
  3. 層ごとの切り分け：データの取得・変換（統合部分）／API のエラーや stop_reason／モデルの出力。
  4. 修正と確認：原因に合った修正。プロンプトやモデルを闇雲に変えない。
  5. 再発防止：失敗したケースを評価データに加える。監視とアラートを見直す。
症状考えられる原因
特定の顧客だけ何も返らない顧客データの取得の例外、空のコンテキスト、refusal、タイムアウト
時間帯によって遅い・失敗するレート制限（429）、過負荷（529）、同時実行数
ある日から品質が落ちたモデル・プロンプト・データの変更（何が変わったか）

この分野のまとめ

  • 安全基準は組織の設定で一律に。プロジェクトの決まりはリポジトリで共有。
  • 開発は計画 → 小さく実装 → テスト → レビュー。
  • 障害は記録で再現条件を特定し、層ごとに切り分ける。
