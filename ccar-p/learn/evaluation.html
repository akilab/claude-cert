評価・テスト・最適化 配点 16%

何を測るか、どう測るか、どう比べるか、問題をどう診断するか、本番でどう見守るかを扱います。LLM のシステムの品質は「評価の仕組み」で決まります。

評価指標を決める

観点指標の例測り方
正確さ正答率、抽出の一致率、根拠への忠実さ正解データとの照合、LLM による採点、人
速度最初のトークンまで（TTFT）、全体の時間。どちらも p50・p95 で見る（用語の解説）計測
費用1件あたりのトークン・金額usage の集計
安全性不適切な依頼への対応、方針違反の率攻撃的な入力のテストセット
セキュリティインジェクションへの耐性、情報漏えいレッドチームのテスト

どれか1つだけを見ると、別の観点が悪化しても気づけません。主要な指標と、副作用を見る指標を組み合わせます。

速度の指標を読む（p50・p95・TTFT・SLA）

速度の要件や監視では、「p95 で 2 秒以内」「TTFT」のような言葉が出てきます。どれも、何を・どの位置で測った値かをはっきりさせるための言葉です。

平均ではなく「分布」で見る

応答時間は、ほとんどのリクエストが速く、ごく一部が極端に遅い、という形になりがちです。このとき平均は、一部の遅いリクエストに引っ張られて上がる一方で、遅い思いをしている利用者がどれだけ遅いかは表しません。そこで、値を小さい順に並べて「どの位置の値か」で見ます。これをパーセンタイル（percentile）といいます。

指標意味読み方
p50（中央値）小さい順に並べて、ちょうど真ん中（50%）の位置の値典型的な利用者の体験
p95下から 95% の位置の値。95% のリクエストはこの時間以内に終わり、残り 5% はこれより遅い遅い側の利用者の体験。SLA で最もよく使う
p99下から 99% の位置の値。100 件に 1 件はこれより遅いさらに遅い側（裾）の体験。件数が多いシステムで重要
平均合計 ÷ 件数費用やトークン量の集計には便利。応答時間の体験は表しにくい

図の例では、p50 は 1.3 秒、p95 は 2.4 秒、平均は 1.78 秒です。平均の 1.78 秒は、典型的な体験（1.3 秒）より遅く、しかも 20 番目の 9.0 秒という極端な遅さは見えません。「平均 2 秒以内」という約束は、20 人に 1 人が 10 秒待たされていても守れてしまいます。だから速度の要件は「p95 で ◯ 秒以内」のように書きます。

注意点：

  • 件数が少ないと p95・p99 は安定しません。20 件の p95 は、たった 1 件の値で決まります。評価や監視では十分な件数で測ります。
  • パーセンタイルは足し算できません。「処理A の p95 ＋ 処理B の p95」は、全体の p95 にはなりません。全体の p95 は、全体の時間を測って求めます。
  • 同じ考え方は、トークン数や費用の分布にも使えます（例：1 件あたりのトークン数の p95）。

TTFT と全体の時間

LLM の応答時間には、2 つの測り方があります。

指標意味短くする方法長くなる要因
TTFT（Time To First Token：最初のトークンまでの時間）リクエストを送ってから、最初の文字が届くまでプロンプトキャッシュ、入力を短くする、思考（effort）を減らす、小さいモデル長い入力、多い思考
全体の時間（end-to-end の時間）リクエストを送ってから、最後の文字が届くまで出力を短くする、小さいモデル、処理の並列化長い出力、ツール呼び出しの往復

ストリーミングは、できた部分から順に届けるしくみです。利用者は最初の文字が届いた時点で読み始められるので、待ち時間の体感は TTFT で決まります。ただし生成そのものは速くならないので、全体の時間は変わりません。

  • 画面に表示しながら読む用途（チャット、オペレーターの支援）→ TTFT が重要
  • 結果をまとめて後続の処理に渡す用途（抽出、分類、バッチ処理）→ 全体の時間が重要

SLA は「測れる定義」で書く

SLA（Service Level Agreement：サービス水準の合意）は、利用者や関係部署と約束する品質の水準です。「応答 1 秒」のようなあいまいな言葉では、後で「守れているか」が争いになります。次の要素をすべて決めて書きます。

決めること例
何を測るかTTFT か、全体の時間か。正答率なら、どの評価データで測るか
どの位置の値かp95（平均ではなく）
どこからどこまでかアプリが API を呼んでから最初の文字を受け取るまで、など
どの期間で集計するか1 か月ごと、など
守れなかったときどうするか報告、原因の調査、改善の計画

例：「TTFT が月次の p95 で 1.5 秒以内（アプリが API を呼んでから最初のトークンを受け取るまで）」。目標の数字は、評価で実際に測った値をもとに、関係者と合意して決めます（期待値の調整と SLA）。

「p95 で ◯ 秒」の要件は「95% のリクエストが ◯ 秒以内」。要件が TTFT か全体の時間かを必ず読み分ける。要件は「満たせば十分」な最低条件で、余った時間は精度に使う。

評価データとテストの仕組み

  • 中身：典型例＋境界例＋本番で失敗したケース。専門家の正解（期待する出力と根拠）つき。
  • 量と多様性：本番の入力の分布を代表するように。生成データで補う場合は人が確認する。
  • 採点の方法を組み合わせる（mixed methods）：
    • コード：形式・完全一致・数値の照合（速く・安く・確実）
    • LLM による採点：要約の質など、柔軟な判断（基準を明確に、人の採点との一致を確認）
    • 人：最終的な品質の基準、難しいケース

A/B テストと繰り返しの改善

  1. 変更は1回に1つ（プロンプト、モデル、検索の設定を同時に変えない）。
  2. まずオフラインの評価セットで確かめる。
  3. 本番で一部の利用者に新しい版を出し（A/B）、十分な件数で比べる（LLM の出力はばらつくため）。
  4. 主要な指標と、副作用（費用・速度・安全性）の両方を見る。
  5. 結果を記録し、採用・見送りを判断する。

問題の診断

「何が変わったか・何が変わっていないか」から原因を絞ります。

症状変わったものまず疑う場所
文書の更新後に、自信満々の誤答文書だけ取り込み・検索（再インデックス、古いチャンク、埋め込みの不一致）
モデルの切り替え後に形式が崩れるモデル挙動の変化（プロンプトの前提、出力の長さ・書式）
特定の入力だけ失敗入力データの形・型、プロンプトの想定外のケース
指示に従わない・ばらつくプロンプト指示の曖昧さ、例の偏り、コンテキストの肥大化
根拠のない内容—資料の不足（検索で取れていない）、「分からない」を許していない
「モデルの重みが勝手に変わった」「temperature のせい」のような、状況と結びつかない原因は誤答の定番。

手段効果注意点

本番の監視

  • エラー率・遅延・費用（システムの健全性）。
  • 出力の品質：一定の割合をサンプリングし、自動採点と人の確認で継続評価。閾値を下回ったら通知。
  • 利用者のフィードバック（役に立った／立たなかった、修正の内容）。
  • 入力の傾向の変化（新しい種類の質問、言語、長さ）。

LLM の品質の低下は HTTP エラーとして現れないことが多いので、出力そのものを測る仕組みが必須です。

この分野のまとめ

  • 指標は多面的に。主要な指標と副作用の指標。
  • 評価データは典型＋境界＋本番の失敗。採点はコード・LLM・人の組み合わせ。
  • 変更は1つずつ、十分な件数で比較。
  • 診断は「何が変わったか」から。
  • 本番は出力の品質まで監視する。
