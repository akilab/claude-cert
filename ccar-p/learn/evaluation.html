評価・テスト・最適化 配点 16%

何を測るか、どう測るか、どう比べるか、問題をどう診断するか、本番でどう見守るかを扱います。LLM のシステムの品質は「評価の仕組み」で決まります。

評価指標を決める

観点指標の例測り方
正確さ正答率、抽出の一致率、根拠への忠実さ正解データとの照合、LLM による採点、人
速度最初のトークンまで、全体の時間（p50・p95）計測
費用1件あたりのトークン・金額usage の集計
安全性不適切な依頼への対応、方針違反の率攻撃的な入力のテストセット
セキュリティインジェクションへの耐性、情報漏えいレッドチームのテスト

どれか1つだけを見ると、別の観点が悪化しても気づけません。主要な指標と、副作用を見る指標を組み合わせます。

評価データとテストの仕組み

  • 中身：典型例＋境界例＋本番で失敗したケース。専門家の正解（期待する出力と根拠）つき。
  • 量と多様性：本番の入力の分布を代表するように。生成データで補う場合は人が確認する。
  • 採点の方法を組み合わせる（mixed methods）：
    • コード：形式・完全一致・数値の照合（速く・安く・確実）
    • LLM による採点：要約の質など、柔軟な判断（基準を明確に、人の採点との一致を確認）
    • 人：最終的な品質の基準、難しいケース

A/B テストと繰り返しの改善

  1. 変更は1回に1つ（プロンプト、モデル、検索の設定を同時に変えない）。
  2. まずオフラインの評価セットで確かめる。
  3. 本番で一部の利用者に新しい版を出し（A/B）、十分な件数で比べる（LLM の出力はばらつくため）。
  4. 主要な指標と、副作用（費用・速度・安全性）の両方を見る。
  5. 結果を記録し、採用・見送りを判断する。

問題の診断

「何が変わったか・何が変わっていないか」から原因を絞ります。

症状変わったものまず疑う場所
文書の更新後に、自信満々の誤答文書だけ取り込み・検索（再インデックス、古いチャンク、埋め込みの不一致）
モデルの切り替え後に形式が崩れるモデル挙動の変化（プロンプトの前提、出力の長さ・書式）
特定の入力だけ失敗入力データの形・型、プロンプトの想定外のケース
指示に従わない・ばらつくプロンプト指示の曖昧さ、例の偏り、コンテキストの肥大化
根拠のない内容—資料の不足（検索で取れていない）、「分からない」を許していない
「モデルの重みが勝手に変わった」「temperature のせい」のような、状況と結びつかない原因は誤答の定番。

トークン・速度・費用の最適化

手段効果注意点
ルーティング（簡単なものは小さいモデル）費用・速度振り分けの精度を評価
プロンプトキャッシュ費用・最初のトークンまでの時間変わらない部分を先頭に
Batches費用 50%即時性がない
出力の長さの管理費用・速度必要な情報を削らない
コンテキストの整理費用・速度・精度必要な情報を残す
effort の調整速度・費用難しい処理の精度

本番の監視

  • エラー率・遅延・費用（システムの健全性）。
  • 出力の品質：一定の割合をサンプリングし、自動採点と人の確認で継続評価。閾値を下回ったら通知。
  • 利用者のフィードバック（役に立った／立たなかった、修正の内容）。
  • 入力の傾向の変化（新しい種類の質問、言語、長さ）。

LLM の品質の低下は HTTP エラーとして現れないことが多いので、出力そのものを測る仕組みが必須です。

この分野のまとめ

  • 指標は多面的に。主要な指標と副作用の指標。
  • 評価データは典型＋境界＋本番の失敗。採点はコード・LLM・人の組み合わせ。
  • 変更は1つずつ、十分な件数で比較。
  • 診断は「何が変わったか」から。
  • 本番は出力の品質まで監視する。
