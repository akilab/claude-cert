作成日：2026-11-22
状態：**第1弾 40問を実装済み**（`assets/data/ccdv-f-challenge.json`、`ccdv-f/challenge.html`）。選ぶ数の分布は 2つ：6問／3つ：24問／4つ：10問、選択肢の数は 5〜7個。根拠は `docs/api-notes.md`（api-notes#節）、`docs/claude-code-notes.md`（cc-notes#節）、試験ガイドと一般的な設計原則（guide）。

## 1. 問題の形式

| 項目 | 決めたこと |
|---|---|
| 問い方 | 「**正しいものをすべて選べ**」または「**誤っているものをすべて選べ**」。選ぶ数は示さない |
| 選択肢の数 | 5〜7個（基本は6個） |
| 選ぶべき数 | 必ず2個以上、かつ全部ではない（最低1つは選ばない選択肢がある） |
| 問題文 | 長め（250〜450字程度）。状況・制約・現在の構成を具体的に書く。必要ならコードや JSON の抜粋を含める |
| 選択肢 | 1つ1つが独立した「記述」（40〜90字程度）。それぞれが重要事項の確認になる |
| 採点 | 全部の選択肢の判断が合って初めて正解。あわせて「6つ中4つの判断が正しい」のように部分点を表示する |

### 選択肢の作り方のルール
- **1選択肢＝1つの重要事項**。同じ事実を2つの選択肢で問わない。
- 誤りの記述は「惜しい誤り」にする：数値・条件・対象のずれ（例：「読み込みは ITPM に数える」）、適用範囲の誤り（例：「すべてのモデルで budget_tokens が使える」）、因果の取り違え。
- 正しい記述と誤りの記述で、**長さ・言い切る言葉（すべて・必ず・だけ）の頻度をそろえる**。正しい記述にも「必ず」を使う（例：「tool_result は必ず直後の user メッセージに置く」）。
- 1問の中で「正しい記述」と「誤りの記述」が両方3つ前後になるよう混ぜる。問い方（正しい／誤っている）は 40問でほぼ半々にする。
- 問題文の条件と矛盾して読める要素を正解に入れない（[content-guidelines.md](content-guidelines.md)）。

### 正確さの担保
最難関は細かい事実を問うため、誤りの混入が最大のリスクになる。
- すべての選択肢に**根拠**（`src`）を付ける。例：`api-notes#7`、`guide`（試験ガイド）、公式ドキュメントの URL。
- `docs/api-notes.md` にない事実は、先に公式ドキュメントで確認してメモに追記してから使う。
- Claude Code の細かい仕様（設定ファイルの場所、コマンド、フック）は、作成前に公式ドキュメントで確認し `docs/claude-code-notes.md` に記録する。
- 変わりやすい数字（料金・既定値）は「2026年11月時点」の前提を問題文に書く。

## 2. 画面と仕組み

- **別ページ**：`ccdv-f/challenge.html`（「最難関演習」）。通常の問題演習とは混ぜない。トップと通常の問題演習の開始画面からリンクする。
- **データ**：`assets/data/ccdv-f-challenge.json`（通常の問題とは別ファイル）。記録も別に保存する（通常の正答率に混ざらない）。
- **エンジン**：既存の `exercises.js` を拡張する（新しい問題形式 `select-all` に対応）。ページは `data-exam="ccdv-f" data-set="challenge"` の薄いページ。
- **開始画面**：解き方、分野の絞り込み、出題（まだ解いていない／間違えた／すべて）、出題数（5問・10問・全部）。難易度の選択はなし。
- **解き方**（2026-11-22 追加）
  - 本番形式（既定）：「正しいもの／誤っているものをすべて選べ」。問い方と同じ側の印（◯／✗）を付けたものが解答。印のない選択肢は「選ばない」扱い。
  - 全選択肢を判定：すべての記述に ◯／✗ を付けるまで解答できない。採点は記述ごとの正誤（`fact`）との一致。帯は青（問い方に関係なく中立）。
  - 記録はどちらも同じ問題に積み上がる。
- **選択肢の操作**：各選択肢の右に「◯ 正しい」「✗ 誤り」のボタン（通常演習の ✕＝候補から外す、とは別。✕ は「誤り」と読まれて逆の意味になるため使わない）。
- **出題画面**
  - 問い方を色つきの帯で目立たせる（緑「正しいものをすべて選べ」／赤「誤っているものをすべて選べ」）。読み違いによる失点を防ぐ。
  - 選んだ数は表示するが、正解の数は表示しない。1つ以上選べば解答できる。
  - 選択肢の消去（✕）は通常と同じく使える。
- **解答後の表示（選択肢ごと）**
  - 記述そのものの正誤：「◯ 正しい記述」／「✕ 誤った記述」
  - あなたの判断が合っていたか：「✓ 判断が正しい」／「✗ 選ぶべきだった」「✗ 選ぶべきではなかった」
  - なぜその記述が正しい／誤りなのかの解説
- **ポイント**：1問ごとに、その問題で確認した重要事項を箇条書きでまとめる（復習用）。
- **結果画面**：完全正解の数、選択肢単位の正答率（例：240個中 205個の判断が正しい）、分野別の成績、間違えた問題の解き直し。

### データの形式
```json
{
  "id": "dvx-api-001",
  "domain": "app",
  "skills": ["Claude API Mechanics"],
  "ask": "correct",                // correct＝正しいものを選ぶ / incorrect＝誤っているものを選ぶ
  "stem": "長い問題文…",
  "options": [
    {"text": "記述", "fact": true, "why": "解説", "src": "api-notes#1"}
  ],
  "point": ["確認した重要事項1", "重要事項2"],
  "learn": "learn/messages-api/index.html#request"
}
```
`fact` は記述が事実として正しいか。選ぶべきかどうかは `ask` と `fact` から決まる（`ask: incorrect` なら `fact: false` を選ぶ）。

### チェック（tools/validate.py に追加）
選択肢 5〜7個／選ぶべき数が2個以上かつ全部ではない／全選択肢に `src` と `why`／正しい記述と誤りの記述の平均の長さの差が 20% 以内／`ask` が 40問でほぼ半々。

## 5. サンプル（形式の確認用）

**Domain 5-3：プロンプトキャッシュ**　**誤っているものをすべて選べ**

> 社内規程アシスタント（Sonnet 5.5）で、約 9,000 トークンの規程を system に置き、`cache_control: {"type": "ephemeral"}` を付けました。リクエストは「tools（3個）→ system（先頭に現在時刻、続いて規程）→ 利用者の質問」の順です。導入後1週間の usage を見ると、ほぼすべてのリクエストで `cache_creation_input_tokens` が約 9,000、`cache_read_input_tokens` が 0 で、費用は導入前より少し増えていました。チームで原因と対策を話し合ったところ、次の意見が出ました。キャッシュの仕様（2026年11月時点）に照らして、**誤っているもの**をすべて選んでください。

| 選択肢 | 正誤 | 根拠 |
|---|---|---|
| A. 毎回変わる現在時刻が規程より前にあるため、先頭からの一致部分が毎回変わり、読み込みにならない | 正しい | api-notes#7 |
| B. 費用が増えたのは、キャッシュの書き込みが通常の入力より高い単価（5分の場合 1.25倍）で課金されるためだ | 正しい | api-notes#7 |
| C. 規程が 512 トークン未満だったらエラーが返るはずなので、長さの問題ではないと言い切れる | **誤り**（最小未満はエラーにならず、キャッシュされないだけ） | api-notes#7 |
| D. キャッシュの読み込みは通常の入力と同じく ITPM（入力トークン／分）の制限に数えられる | **誤り**（読み込みは ITPM に数えない） | api-notes#10 |
| E. 区切りは tools・system・messages を合わせて最大4つまで置ける | 正しい | api-notes#7 |
| F. ttl を "1h" にすれば、先頭の時刻が変わっても1時間は同じキャッシュが読まれる | **誤り**（有効期限を延ばしても、プレフィックスが一致しなければ読まれない） | api-notes#7 |

→ 選ぶべきもの：C・D・F（3つ）。ポイント：キャッシュは「先頭からの一致」がすべて／書き込みは割高、読み込みは割安／最小の長さ未満はエラーにならない／読み込みは ITPM に数えない。
