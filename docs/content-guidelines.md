# コンテンツ作成ルール

問題集と学習コンテンツを作るときに守ること。作業のたびに参照する。

## 1. 出典と正確さ

- 試験範囲は `docs/exam-research.md`（CCDV-F）と `docs/ccar-p-research.md`（CCAR-P）のブループリントにもとづく。
- API の仕様は `docs/api-notes.md` にもとづく。メモにない仕様を問題や疑似環境に入れるときは、先に公式ドキュメントで確認してメモに追記する。
- 基準は現行の試験ガイド v1.0。12月7日の改訂内容は、指示があるまで入れない。
- 料金やモデル名など変わりやすい数字は、問題の正解の根拠にしない。使う場合は「2026年11月時点」と書く。

## 2. 試験の機密を守る

- 問題はすべてオリジナルで作る。受験記などに書かれた実際の試験問題を再現したり、言い換えたりしない。
- 公式ガイドのサンプル問題は、そのまま転載しない。考え方の解説にとどめる。

## 3. 問題の作り方

- 形式は本番に合わせる：単一選択（4択）と複数選択（5択から2つなど。選ぶ数を問題文に書く）。
- 問題文には **状況・要件・制約** を入れ、決め手になる語（「コスト最優先」「再利用したい」「信頼できない入力」など）を含める。
- 誤答は「もっともらしいが的を外したもの」にする。
  - 要件の一部しか満たさない
  - 強制力がない（プロンプトでお願いするだけ）
  - 関係のない調整（temperature、モデルの大きさ）
  - 機能の範囲の誤解
  - 検知・補完の対策で、原因を取り除いていない
- 明らかに不自然な選択肢や、「すべて正しい」のような選択肢は使わない。
- **正解に、問題文の条件と矛盾して読める要素を入れない**。例：「2秒以内が必須」の問題で、正解に「難しい案件は別の経路で処理する」（2秒を超えると読める）を含めない。正解は条件をすべて満たすことが一読で分かるようにする。
- **選択肢の長さをそろえる**。正解だけが詳しく長いと、内容を理解していなくても長さで当てられてしまう。
  - 正解は要点だけに絞る。詳しい理由は解説（why）に書く。
  - 誤答にも「もっともらしい理由」を添えて、正解と同じくらいの長さにする。
  - `tools/validate.py` で確認する：正解が誤答の最長より 1.2倍を超えて長い問題はエラー。正解が一番長い問題の割合は 35% 以下（4択の偶然は約25%）。

### 難易度
| レベル | 内容 |
|---|---|
| 基礎（1） | 用語と仕組みを知っているか（例：stop_reason の意味） |
| 標準（2） | 状況に合った方法を選べるか（例：要件に合う API の選択） |
| 応用（3） | 複数の条件を比べて判断できるか、原因を切り分けられるか |

CCAR-P は標準と応用を中心にする。

## 4. 解説の書き方

- **選択肢ごと** に、なぜ正しいか／なぜ違うかを書く。
- 最後に「ポイント」として、覚えるべきことを1〜2文でまとめる。
- 仕組みや流れが関わる問題には図（SVG）を付ける。
- 関連する学習コンテンツのページにリンクする。

## 5. 文章

- です・ます調。1文を短くする。専門用語は初出で説明する。
- 英語の用語は、試験が英語であることを考えて、日本語の後に英語を併記する（例：最小権限（least privilege））。
- 画面の文言では「クイズ」を使わず「問題演習」と書く。

## 6. 学習ページの書き方（2026-11-23 追加）

対象読者を試験ごとに分ける。

| 試験 | 想定する読者 | 書き方 |
|---|---|---|
| CCDV-F | **初学者**（API や LLM の開発経験が浅い人も含む） | 初出の用語は必ず説明する。抽象的な説明だけで終わらせず、**サンプル**（プロンプト、JSON、コード、悪い例と良い例）を付ける |
| CCAR-P | 実務経験のあるエンジニア・アーキテクト | 前提知識はある程度高く見積もってよい。ただし指標の定義（p95 など）や、判断の決め手になる用語は説明する |

部品（`assets/css/learn.css`）：
- 用語の箱：`<div class="terms"><dl><dt>用語</dt><dd>説明</dd></dl></div>`。その節で初めて出る用語を、節の最初か直後にまとめる。
- サンプルの箱：`<div class="sample"><p class="sample-title">サンプル：…</p><pre><code>…</code></pre><p>読み方の説明</p></div>`。
- 悪い例と良い例の比較：`<div class="compare"><div class="bad">…</div><div class="good">…</div></div>`。
- 1つの節は「一言でいうと → サンプル → なぜそうするか → 試験のポイント」の順を基本にする。
- **実物の形を見せる**：説明だけで終わらせず、実際のリクエスト・レスポンス・コード・設定ファイルの形をサンプルで示す。API キーなどの秘密の値は**ダミー**で示す（`sk-ant-api03-DUMMY…` のように `DUMMY` を含め、本物の長さにしない。秘密情報の検出ツールに誤って引っかからないようにするため）。

## 7. 問題データの形式

`assets/data/<exam>.json`。`tools/validate.py` で確認する。

```json
{
  "id": "dv-api-001",
  "domain": "app",
  "skill": "Claude API Mechanics",
  "level": 1,
  "type": "single",
  "stem": "問題文",
  "options": [
    {"text": "選択肢", "correct": true, "why": "なぜ正しいか"},
    {"text": "選択肢", "correct": false, "why": "なぜ違うか"}
  ],
  "point": "ポイント",
  "diagram": "assets/img/xxx.svg",
  "learn": "learn/messages-api/index.html#stop-reason"
}
```

- `type` は `single`（正解1つ）か `multi`（正解2つ以上。選ぶ数は正解の数）。
- `diagram` と `learn` は任意。パスはサイトのルートからの相対パス。
