Messages API をしくみから学ぶ

Claude をアプリから使うときの入口が Messages API です。CCDV-F では「Claude API Mechanics」（6.8%）を中心に、ツール・キャッシュ・コストなど多くの分野の土台になります。CCAR-P でも、設計の判断の前提として必要です。

全体像：1回のやり取り

Messages API は、「会話の内容を JSON で送ると、Claude の返答が JSON で返る」 だけのシンプルな HTTP の API です。

  1. アプリが POST https://api.anthropic.com/v1/messages に、ヘッダー（API キーなど）とボディ（モデル・会話・設定）を送る。
  2. API がリクエストを検証し、Claude が返答を生成する。
  3. レスポンスとして、返答の内容（content）、止まった理由（stop_reason）、使ったトークン数（usage）が返る。

このシンプルさの裏返しとして、会話の履歴の管理、ツールの実行、再試行などは、すべてアプリ側の仕事になります。試験ではこの「アプリの責任の範囲」がよく問われます。

リクエストの形

ヘッダー

ヘッダー内容
x-api-keyAPI キー。サーバー側で保管し、ブラウザやソースコードに置かない。
anthropic-version必須。API の挙動のバージョン（例：2026-10-21）。同じバージョンを指定している限り、挙動が急に変わらない。
content-typeapplication/json

ボディ（必須の3項目）

{
  "model": "claude-sonnet-5-5",        // どのモデルで
  "max_tokens": 1024,                  // 出力をどこまで許すか（上限）
  "messages": [                        // 会話の内容
    {"role": "user", "content": "こんにちは"}
  ]
}

よく使う任意の項目：

項目用途
system役割・方針・制約など、会話全体に効く指示
stop_sequencesこの文字列が出たら止める
streamtrue で少しずつ受け取る（ストリーミング）
tools／tool_choiceツールの定義と、使わせ方
thinking／output_config.effort思考（推論）の設定と量の目安
output_config.format構造化出力（JSON スキーマで出力の形を決める）
cache_controlプロンプトキャッシュ

注意（API バージョン 2026-10-21）：temperature・top_p・top_k は廃止され、送ると 400 エラーになります。古い教材やサンプルコードには残っていることがあるので気をつけましょう。

レスポンスの形

{
  "id": "msg_01...",
  "type": "message",
  "role": "assistant",
  "model": "claude-sonnet-5-5",
  "content": [ {"type": "text", "text": "こんにちは！…"} ],   // ブロックの配列
  "stop_reason": "end_turn",                                  // なぜ止まったか
  "stop_sequence": null,
  "usage": {                                                  // 使ったトークン数
    "input_tokens": 12,
    "cache_creation_input_tokens": 0,
    "cache_read_input_tokens": 0,
    "output_tokens": 48
  }
}
  • content は配列：text のほかに、tool_use（ツールの要求）や thinking（思考）のブロックが並ぶことがあります。テキストだけを取り出すなら、type が text のブロックを集めます。
  • usage を記録する：費用の計算、異常な使用量の検知、キャッシュの効果の確認に使います。入力の合計は input_tokens + cache_creation_input_tokens + cache_read_input_tokens です。
  • レスポンスヘッダーの request-id は、問題の調査や問い合わせに必要なので、ログに残します。

ステートレス：履歴はアプリが持つ

Messages API は前回のやり取りを覚えていません。会話を続けるには、これまでの user と assistant のやり取りを 毎回すべて messages に入れて送ります。

  • role は user と assistant の2種類。同じ role が続くと1つのターンにまとめられます。
  • system は messages の中ではなく、トップレベルの system パラメータに書きます。
  • 履歴が長くなるほど、入力トークン（＝費用と待ち時間）が増えます。話題が変わったら新しい会話にする、古い部分を要約する、といった工夫が必要です（セッションの衛生管理・コンテキストエンジニアリング）。
「会話 ID を送れば続きになる」「API が覚えている」といった選択肢は誤り。履歴の管理はアプリの責任。

content ブロックの種類

typeどこに入る内容
textuser／assistant文章
imageuser画像（base64・URL・Files API）
documentuserPDF やテキストの文書
tool_useassistantClaude からのツールの要求（id・name・input）
tool_resultuserアプリが返すツールの結果（tool_use_id で対応づけ）
thinkingassistant思考の内容と署名。変えずに送り返す

stop_reason：なぜ止まったか

アプリは stop_reason を見て、次に何をするかを決めます。

値意味アプリの対応
end_turn自然に書き終えたそのまま使う
max_tokens上限に達して途中で切れた上限を上げる／続きを生成する／短く出させる
stop_sequence指定した文字列が出た想定どおりの停止として扱う
tool_useツールを呼んでほしい実行して tool_result を返し、再度呼ぶ
pause_turnサーバーツールのループが上限に達した返ってきた内容をそのまま送り返して続ける
refusal応答を断った（HTTP 200）stop_details を確認する
model_context_window_exceededコンテキストウィンドウがいっぱい途中で切れたものとして扱う

プリフィルは使えない（新しいモデル）

以前は、messages の最後を assistant にして「{」などを書いておき、その続きから書かせる「プリフィル」という技法がありました。Claude 4.6 以降のモデルではプリフィルは 400 エラーになります。出力の形を決めたいときは、構造化出力を使います。

ストリーミング

"stream": true にすると、返答ができた部分から少しずつ届きます（Server-Sent Events）。生成の速さや料金は同じですが、利用者が最初の文字を見るまでの時間が短くなり、体感が大きく改善します。

  • 文章は text_delta、ツールの入力は input_json_delta（JSON の断片。全部つなげてからパース）で届きます。
  • stop_reason と出力トークン数は、最後のほうの message_delta で届きます。
  • 途中で error イベント（例：overloaded_error）が来ることがあります。HTTP は 200 のままなので、イベントの中身で判断します。
  • 知らない種類のイベントが来ても、無視して処理を続けられるように作ります。

ツール利用（tool use）のループ

ツールを定義すると、Claude は必要に応じて「このツールをこの入力で呼んで」と要求します。Claude は要求するだけで、実行するのはアプリです（自分で定義したクライアントツールの場合）。

ツールの定義

{
  "name": "get_weather",
  "description": "指定した都市の現在の天気と気温を返す。利用者が天気・気温を尋ねたときに使う。",
  "input_schema": {
    "type": "object",
    "properties": { "city": {"type": "string", "description": "都市名（例：大阪）"} },
    "required": ["city"]
  }
}

description が最も重要です。Claude は名前と説明を読んで、いつ・どう使うかを判断します。何をするか、いつ使うか、入力の意味、何が返るかを具体的に書きます。

結果の返し方（よくある誤り）

[
  {"role": "user", "content": "大阪の天気は？"},
  {"role": "assistant", "content": [                       // ← 返ってきた内容をそのまま入れる
    {"type": "tool_use", "id": "toolu_01A", "name": "get_weather", "input": {"city": "大阪"}}
  ]},
  {"role": "user", "content": [                            // ← 直後の user に
    {"type": "tool_result", "tool_use_id": "toolu_01A",    // ← id を対応づける
     "content": "{\"weather\":\"晴れ\",\"temp_c\":18}"}      // ← content の先頭に置く
  ]}
]
  • tool_result は、tool_use を含む assistant の直後の user メッセージに置く。
  • tool_result は user の content の先頭に置く。テキストを添えるなら後ろに。
  • 複数のツールが並列に呼ばれたら、1つの user メッセージにすべての結果を入れる。
  • ツールが失敗しても tool_result は返す。is_error: true を付け、何が起きたかを簡潔に書く。
  • API はステートレスなので、2回目以降も tools の定義を毎回送る。

tool_choice

値意味
auto使うかどうかは Claude が決める（既定）
any／tool必ずツール（指定したもの）を使う。Opus 5.5・Sonnet 5.5 などは非対応
noneツールを使わない

クライアントツールとサーバーツール

自分で定義するツールはアプリが実行します（クライアントツール）。一方、Web 検索（web_search）などのサーバーツールは Anthropic 側で実行され、結果がレスポンスに含まれて返ります。

構造化出力

後続のシステムが機械的に読む出力は、output_config.format に JSON スキーマを指定して、形を保証します。

"output_config": {
  "format": {
    "type": "json_schema",
    "schema": {
      "type": "object",
      "properties": {
        "category": {"type": "string", "enum": ["billing", "technical", "cancellation", "other"]},
        "urgency":  {"type": "string", "enum": ["low", "medium", "high"]}
      },
      "required": ["category", "urgency"],
      "additionalProperties": false
    }
  }
}
  • 値の候補は enum で固定し、additionalProperties: false で余計な項目を出させない。
  • 再帰、oneOf、数値の範囲や文字数の制約（minimum・maxLength など）は使えない。範囲の確認はアプリ側で行う。
  • 形が保証されても、内容が業務的に正しいかは別の話。重要な値はアプリで検証する。
  • ツールの入力の形を保証したいときは、ツール定義に "strict": true を付ける方法もある。

画像の入力

{"role": "user", "content": [
  {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": "iVBORw0K..."}},
  {"type": "text", "text": "この領収書の合計金額は？"}
]}
  • 対応形式は JPEG・PNG・GIF・WebP。media_type は画像の中身と一致させる。
  • 1枚あたり最大 10MB（base64）、最大 8000×8000 px。
  • トークン数の目安は ⌈幅/28⌉ × ⌈高さ/28⌉。大きい画像は自動で縮小される。
  • 画像は質問のテキストより前に置くと、精度が上がりやすい。

思考（thinking）と effort

思考を有効にすると、Claude は回答の前に推論を行い、その内容が thinking ブロックとして返ります。複雑な推論や多段の判断で精度が上がります。

設定内容対象
{"type": "adaptive"}考えるかどうか・どれだけ考えるかを Claude が判断Claude 4.6 以降
output_config.effortlow／medium／high／xhigh／max。思考の量と速さ・費用の目安新しいモデル
{"type": "enabled", "budget_tokens": N}思考の予算を指定（N ≥ 1024、N < max_tokens）旧世代。Claude 4.7 以降は 400
  • 思考トークンは出力として課金され、max_tokens の中に含まれる。
  • ツールのループでは、thinking ブロックを変えずにそのまま送り返す（変えると 400）。
  • 簡単な処理は effort を下げて速く・安く、難しい処理は上げて精度を優先する。

プロンプトキャッシュ

毎回同じ長い指示や資料を送っているなら、プロンプトキャッシュで費用と最初のトークンまでの時間を大きく下げられます。

  • cache_control: {"type": "ephemeral"} を付けたブロックまでが区切り（最大4つ）。トップレベルに付ける自動キャッシュもある。
  • キャッシュされる順番は tools → system → messages。変わらない内容を先に、変わる内容を後に置く。
  • 有効期限は既定 5分（"ttl": "1h" で1時間）。読み込むたびに延長される。
  • 料金：書き込み＝入力の 1.25倍（1時間なら 2倍）、読み込み＝0.1倍程度（モデルによりさらに安い）。
  • 最小の長さ（例：Opus 5.5・Sonnet 5.5・Haiku 5.5 は 512 トークン）に満たないと、エラーにはならずキャッシュされないだけ。
  • 効果は usage の cache_creation_input_tokens（書き込み）と cache_read_input_tokens（読み込み）で確かめる。
「同じ長い system を毎回送っていて、速度と費用の両方を改善したい」→ 変わらない部分を先頭に置いてキャッシュ。切り詰めやモデルの縮小は、必要な情報や品質を失う。

エラーと再試行

{"type": "error",
 "error": {"type": "rate_limit_error", "message": "..."},
 "request_id": "req_011..."}
  • 429・500・529：一時的。待って再試行（429 は retry-after の秒数、その他は指数バックオフ＋ゆらぎ）。回数には上限を付ける。
  • 400・401・403・404：リクエストや設定の誤り。再試行しても同じなので、原因を直す。
  • 公式 SDK は一時的なエラーを既定で2回まで自動で再試行する。二重に再試行を組まないよう注意。
  • レート制限は RPM（リクエスト／分）、ITPM（入力トークン／分）、OTPM（出力トークン／分）で管理され、トークンバケット方式で回復する。キャッシュの読み込みは ITPM に数えない。

Message Batches API

  1. 作成：POST /v1/messages/batches に、custom_id と params（Messages のボディ）の組を並べて送る。
  2. 状態の確認：GET /v1/messages/batches/{id}。processing_status が ended になるまで待つ。
  3. 結果の取得：GET …/{id}/results（JSONL）。順番は保証されないので custom_id で対応づける。
  • 料金は通常の 50%。最長24時間で処理（終わらないものは expired）。
  • 1バッチ最大 100,000 件または 256MB。結果は29日間取得できる。
  • 個々のリクエストの失敗は、バッチ全体ではなく、その1件の errored として返る（課金されない）。
  • ストリーミングは使えない。利用者が画面で待つ処理には向かない。

この章のまとめ

  • 必須は model・max_tokens・messages、ヘッダーは x-api-key・anthropic-version。
  • API はステートレス。履歴・ツールの実行・再試行はアプリの仕事。
  • stop_reason で次の動作を決める。tool_use なら実行して tool_result を返す。
  • 速く見せたい → ストリーミング。急がない大量処理 → Batches（50%）。同じ長い前置き → キャッシュ。
  • 429・5xx は待って再試行、4xx は直す。
