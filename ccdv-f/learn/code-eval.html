Claude Code と評価・デバッグ 配点 3.1%＋2.6%

配点は小さい2分野ですが、Claude Code の設定は構成管理やセキュリティの問題にも登場します。デバッグの切り分けは、すべての分野の「原因を問う」問題の基礎です。

CLAUDE.md の階層

  • チームの決まり（テストのコマンド、コーディング規約、ブランチの運用など）は、リポジトリの CLAUDE.md に書いて共有する。
  • 個人の好みは個人用に。組織全体の方針は、管理者が配布する設定で強制できる。
  • リポジトリの初期化（/init）で、コードベースを調べて CLAUDE.md のたたき台を作れる。

Claude Code の構成要素

要素内容
CLAUDE.md／Rules常に読み込まれる指示・決まり
Skillsやり方の知識。関係するときだけ読み込まれる
Commands（スラッシュコマンド）組み込み（/clear、/compact、/init など）と、カスタム（定型の指示を保存）
Agents（サブエージェント）役割と権限を限定した子のエージェント
Agent Memoryセッションをまたいで残す記録
settings.json権限（許可・拒否）、フック、環境変数、モデルなどの動作の設定

使い分け：決まり → CLAUDE.md、繰り返す指示 → カスタムコマンドやスキル、動作の設定と強制 → settings.json とフック。

ヘッドレスモードと自動化

claude -p "この差分を要約して、リスクを3点挙げて" --output-format json
  • ヘッドレスモード（-p）は、対話画面を使わずに1回の指示で実行し、結果を出力する。CI やスクリプトからの自動化に使う。
  • 出力形式を JSON やストリーミングにして、後続の処理で使える。
  • 自動実行では、必要な権限だけを許可する。
  • auto モードは権限モードの1つ。利用者に確認を出す代わりに、別の分類用のモデルが操作を実行前に審査する。明示的な ask のルールは引き続き確認を出す。
  • bypassPermissions は確認をすべて省略するモードで、隔離された環境でのみ使う。CI では --allowedTools で必要なツールだけを許可する。

デバッグとエラー処理

原因の切り分け

症状まず疑う場所
HTTP エラー（4xx・5xx）リクエストの形式・認証・レート制限・障害
出力が途中で切れるstop_reason が max_tokens
ツールの入力がおかしい（先頭のゼロが消える等）input_schema の型、アプリ側の変換
JSON のパースに失敗構造化出力の未使用、検証の欠如
内容が誤っている・根拠がない渡した資料・検索結果、プロンプト、モデルの選択

記録すべき情報

request-id、モデルとプロンプトの版、stop_reason、usage、エラーの種類、ツールの入出力（個人情報は伏せる）。これがあれば、再現と切り分けができます。

回復の方法の選び方

  • 一時的なエラー → 上限つきの再試行（指数バックオフ）。
  • 入力の誤り → 直す。利用者に分かるように伝える。
  • 出力の形の誤り → 検証して再生成、または既定の処理。
  • 続く障害 → フォールバック（代替の処理・別モデル）と、利用者への案内。

この分野のまとめ

  • チームの決まりはリポジトリの CLAUDE.md。繰り返す指示はカスタムコマンド・Skills。
  • 自動化はヘッドレスモード（-p）。
  • トレースで層ごとに切り分ける。統合部分か、モデルの出力か。
