Claude Code の設定と権限（どのファイルに何を書くか） Claude Code・セキュリティ

Claude Code には、CLAUDE.md、rules、settings.json など、設定のファイルがいくつもあります。試験では「この目的なら、どのファイルに何を書くか」がよく問われます。この章では、ファイルの役割と関係を図で整理し、権限（permissions）の書き方を説明します。

試験との関係：「Claude Code」の分野が中心です。権限やフックは「セキュリティと安全」（Claude Hooks）、設定ファイルの共有は「構成管理」の問題にも出てきます。ふだんの開発でもそのまま使える知識です。根拠は Claude Code の公式ドキュメント（2026-11-28 に確認）です。

いちばん大事な区別：お願いか、強制か

設定のファイルは、大きく2種類に分かれます。

  • 文脈（お願い）：CLAUDE.md・rules・スキルは、Claude が読む文章です。プロジェクトの決まりを伝えるのに使います。公式ドキュメントも「強制される設定ではなく、文脈として扱われる」と説明しています。
  • 設定（強制）：settings.json に書く権限のルールやフックは、Claude Code というプログラムが判定します。モデルの判断に関係なく、必ず効きます。
「確実に」「必ず」「絶対に読ませない」と問われたら、CLAUDE.md ではなく settings.json の deny ルールやフック。CLAUDE.md に「絶対に」と強く書いても、お願いであることは変わりません。

どのファイルに何を書くか：一覧

ファイルの置き場所は、ホームフォルダ（自分のすべてのプロジェクト）とプロジェクトのフォルダの2か所に分かれます。

~/.claude/                     ← 自分のすべてのプロジェクトに効く
├── CLAUDE.md                  自分の好み（「説明は日本語で」など）
├── rules/                     自分の決まりを話題ごとに
└── settings.json              自分の権限・フック・環境変数

my-project/                    ← このプロジェクトだけ
├── CLAUDE.md                  チームの決まり（Git で共有）
├── CLAUDE.local.md            自分だけのメモ（Git に入れない）
├── .mcp.json                  チームで使う MCP サーバー
└── .claude/
    ├── settings.json          チームの権限・フック（Git で共有）
    ├── settings.local.json    自分だけの設定（Git に入れない）
    ├── rules/                 話題ごと・フォルダごとの決まり
    ├── skills/                やり方の手順（必要なときに読む）
    └── agents/                サブエージェント
ファイル書くもの共有

（./.claude/CLAUDE.md でもよい）		ビルド・テストのコマンド、コーディング規約などのチームの決まりGit で共有
./CLAUDE.local.md自分の環境の URL など、自分だけのメモ自分だけ

.claude/settings.local.jsonこのプロジェクトでの自分だけの権限など自分だけ

見分け方：名前に .local が付くものは「自分だけ・Git に入れない」。~/（ホーム）にあるものは「自分のすべてのプロジェクト」。プロジェクトの中で .local が付かないものは「チームで共有」。

CLAUDE.md：毎回伝えたい決まり

CLAUDE.md は、Claude Code が起動したときに読む決まりのファイルです。

# プロジェクトの決まり
- テストは `npm test` で実行する
- 型チェックは `npm run typecheck`
- コミットの前に必ずテストを通す
- 詳しいコーディング規約は @docs/style.md を参照
  • 200行未満が目安。長くなったら rules に分けるか、@パス で別のファイルを取り込む（取り込みは最大4段まで）。
  • ユーザー・プロジェクトなど複数の CLAUDE.md は、上書きではなく、つなげて読まれる。
  • /init でコードベースを調べてたたき台を作れる。/memory で編集できる。
  • CLAUDE.md がないときは、AGENTS.md を読む。

rules：話題ごと・フォルダごとの決まり

.claude/rules/ に、1つの話題につき1つの Markdown ファイルを置きます。CLAUDE.md が長くなったときに、話題ごとに分けて整理するための場所です。

いちばんの特徴は、paths を書くと、そのファイルを扱うときだけ読み込まれることです。

---
paths:
  - "src/api/**/*.ts"
---
# API の決まり
- すべての API でエラーの形を { code, message } にそろえる
- 入力は必ず検証してから使う

必要なときだけ読むので、コンテキストを無駄に使わない

  • paths がない rules は、起動時に .claude/CLAUDE.md と同じ優先度で読まれる。
  • 自分用の rules は ~/.claude/rules/ に置く。
  • rules も CLAUDE.md と同じく文脈（お願い）。強制はできない。
伝えたいこと置き場所
毎回の作業で必要な事実（テストのコマンド、全体の規約）CLAUDE.md
特定の種類のファイルやフォルダだけの決まりrules（paths つき）
特定の作業の手順（リリースの手順、レビューのやり方）スキル

settings.json：動作の設定と優先順位

settings.json には、権限のルール・フック・環境変数・使うモデルなどを JSON で書きます。同じ項目が複数のファイルにあるときは、次の順に強いほうが使われます。

ただし、allow・ask・deny のような一覧（配列）は、上書きではなく合算されます。たとえば、ユーザーの設定の deny と、プロジェクトの設定の deny は、両方とも効きます。上書きの順番が効くのは、使うモデルのように値が1つの項目です。

{
  "permissions": {
    "allow": ["Bash(npm test)", "Bash(npm run lint)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./secrets/**)"]
  },
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npm run format" }] }
    ]
  },
  "env": { "NODE_ENV": "development" }
}

permissions は権限のルール、hooks はフック（この例では、編集・書き込みのあとに整形のコマンドを実行）、env は環境変数です。

権限のルールの書き方

権限のルールは3種類です。

種類意味使う場面
allow確認なしで使ってよいテストやリントなど、安全でよく使うコマンド
ask毎回、利用者に確認するpush など、使うことはあるが慎重にしたい操作
deny使わせない秘密の情報を読む、危険な操作

判定の順番：deny がいつも勝つ

  • 最初に一致したもので決まります。書いた順番や、ルールが具体的かどうかは関係ありません。
  • どこか1つのファイルで deny されたものは、ほかのファイルの allow では許可できません。
  • フックが「許可」と返しても、deny は上書きされません。

ルールの書き方

書き方意味
Bash(npm run test *)「npm run test 」で始まるコマンド（前方一致）
Bash(npm run build)このコマンドだけ（完全一致）
Read(./.env)今のフォルダの .env を読む
Read(./secrets/**)secrets フォルダの中のすべて（.gitignore と同じ書き方）
Edit(~/.zshrc)~/ はホームフォルダから
WebFetch(domain:example.com)このドメインのページを取ってくる
mcp__github__*github という MCP サーバーのすべてのツール
Agent(Explore)Explore というサブエージェントを使う

&& や | でつないだコマンドは、1つずつに分けて判定され、すべてが許可されていないと確認なしでは動きません。

Bash のルールの弱点：コマンドの引数を絞るルールは、すり抜けられることがあります。たとえば Bash(curl *) を deny にしても、/usr/bin/curl や sh -c 'curl …' は止められません。外への通信を確実に止めたいときは、Web の取得を WebFetch(domain:…) に限る、PreToolUse のフックで検査する、サンドボックスでネットワークを制限する、などを組み合わせます。

今のルールの一覧は、Claude Code の中で /permissions を実行すると、どの settings.json から来たルールかと一緒に見られます。確認の画面で「Yes, and don't ask again」を選ぶと、そのルールが .claude/settings.local.json に allow として保存されます。

権限モード

ルールに一致しない操作をどう扱うかは、権限モードで決まります。対話中は Shift＋Tab で切り替え、settings.json の permissions.defaultMode で最初のモードを決められます。

モード動き
default必要に応じて確認する（画面では Manual）
acceptEdits作業フォルダの中のファイル編集などを、確認なしで行う
plan読み取り中心で調べ、計画を立てる。ソースは変更しない
auto確認の代わりに、別の分類用のモデルが実行前に操作を審査する
dontAsk確認が必要な操作は、聞かずに拒否する
bypassPermissions確認を省く。隔離された環境でだけ使う
  • auto と bypassPermissions を最初のモードにする設定は、プロジェクトやローカルの settings.json に書いても効きません。ユーザーや組織の設定、または --permission-mode で指定します。共有のリポジトリに書かれた設定で、勝手に確認が省かれないようにするためです。
  • 組織で禁止したいときは、管理設定に "permissions": { "disableBypassPermissionsMode": "disable" } と書きます。

フックとサンドボックス

  • フックは settings.json の hooks に書きます。PreToolUse（ツールの実行前）で終了コード 2 を返すと、権限のルールより前にその操作を止められます。詳しくは用語集の フック。
  • サンドボックス（sandbox.enabled）は、OS の仕組みで、シェルのコマンドが触れるファイルやネットワークを制限します。Bash のルールのすり抜けにも効きます。

この章のまとめ

  • CLAUDE.md・rules・スキルは「文脈（お願い）」。settings.json の権限・フック・サンドボックスは「強制」。確実に止めたいなら後者。
  • .local が付くものは自分だけ（Git に入れない）。~/ にあるものは自分のすべてのプロジェクト。それ以外のプロジェクトのファイルはチームで共有。
  • CLAUDE.md は毎回必要な決まり。rules は話題ごと・フォルダごとの決まりで、paths を付けると関係するファイルを扱うときだけ読まれる。
  • 設定の強さは 組織 ＞ コマンドライン ＞ ローカル ＞ プロジェクト ＞ ユーザー。ただし allow・ask・deny は合算される。
  • 判定は deny → ask → allow。deny がいつも勝つ。Bash の引数を絞るルールはすり抜けられるので、フックやサンドボックスを重ねる。
  • auto と bypassPermissions は、プロジェクトの設定からは最初のモードにできない。
