モデル選択と最適化 配点 16.8%

LLM の基本的な性質、SDK と API の関係、モデルの選び方、トークンと費用の管理を扱います。「なぜそう動くのか」が分かると、他の分野の問題も解きやすくなります。

この章の前提：はじめに（前提知識）の トークン・コンテキスト・ストリーミング・API を呼んでみる（SDK）

LLM の基本

トークン

LLM は文章をトークンという単位で扱います。英語では1単語が1〜数トークン、日本語では1文字が1トークン前後です。料金・速度・コンテキストの上限は、すべてトークン数で決まります。

コンテキストウィンドウ

大きく入れられても、入れるほど遅く・高くなり、重要な情報が埋もれやすくなります。必要なものを選んで入れるのがコンテキストエンジニアリングです（→ コンテキスト）。

次のトークンの予測と非決定性

LLM は「次に来るトークン」を確率的に選び続けて文章を作ります。そのため同じ入力でも出力が変わりうる（非決定的）という性質があります。

  • 品質は1回の結果ではなく、多くのケース × 複数回の評価で判断する。
  • 出力を機械で使うなら、構造化出力と検証で形を守る。
  • API バージョン 2026-10-21 では temperature などのサンプリングの調整項目は廃止されており、プロンプト・構造化出力・effort などで制御する。

SDK と API（Technical Fundamentals）

Messages API・クライアント SDK・Claude Agent SDK・Claude Code の違いは Messages API と SDK で図を使って整理しています。

このスキルは 6.1% と大きめです。公式の SDK（Python・TypeScript など）は、REST API を包んだ薄い層です。

  • 型、認証ヘッダーの付与、一時的なエラーの自動再試行（既定2回）、タイムアウト、ストリーミングの処理を提供する。
  • SDK の再試行の上に、さらに自前の無制限な再試行を重ねない。回数・タイムアウトを要件に合わせて設定し、最後まで失敗したときの処理を書く。
  • ストリーミングは SSE（HTTP の上で、サーバーから順にイベントを送る方式）。双方向の通信が必要なリアルタイムの仕組み（音声など）では WebSocket が使われることもある。

モデルの選び方とトレードオフ

Haiku

  • 最も速く安い
  • 大量の分類・抽出・要約
  • サブエージェントの単純作業

Sonnet

  • 品質と費用のバランス
  • 多くの本番用途、コーディング

Opus

  • 最も高性能
  • 難しい推論、複雑なエージェント、計画役
  1. 要件（品質・速度・費用）を数字で決める。
  2. 小さいモデルから評価し、要件を満たす最小のものを選ぶ。
  3. 処理ごとに使い分ける（例：一次分類は Haiku、難しい判断は Opus）。

モデルの更新による挙動の変化

新しいモデルは全体として賢くなっても、指示の解釈、出力の長さや書式、対応するパラメータが変わることがあります（例：プリフィルや budget_tokens が使えなくなる）。移行ガイドを確認し、評価セットで新旧を比べてから切り替えます。

トークンと費用の管理

費用の計算

費用 ＝ 入力トークン × 入力単価 ＋ 出力トークン × 出力単価
（キャッシュ書き込み：入力単価 × 1.25、読み込み：入力単価 × 0.1 程度）
（Batches：全体の 50%）

例：入力 $2・出力 $10（100万トークンあたり）のモデルで、入力 1,500・出力 500 トークンを1日10万件 → 入力 $300＋出力 $500＝$800/日。出力は単価が高いので、出力の長さの管理がよく効きます。

費用を下げる手段

手段効く場面
モデルの使い分け（ルーティング）簡単な処理が多い
プロンプトキャッシュ同じ長い前置きを繰り返し送る
Message Batches急がない大量処理
出力の長さの指示・max_tokens必要以上に長い出力
コンテキストの整理履歴やツール出力が膨らんでいる
effort の調整思考が不要な簡単な処理

使用量の追跡

レスポンスの usage を記録して、機能別・利用者別の費用を集計し、異常な増加を検知します。送る前の見積もりには count_tokens エンドポイントが使えます。

この分野のまとめ

  • トークンが料金・速度・上限を決める。出力は単価が高い。
  • LLM は非決定的。評価は件数と回数で。
  • 要件を満たす最小のモデルから評価。処理ごとに使い分ける。
  • モデルの更新は評価してから。SDK の再試行を理解して二重にしない。
