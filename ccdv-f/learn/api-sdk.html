Messages API と SDK（違いとつまずきやすい点） 全分野

Claude を自分のプログラムから使う方法には、Messages API、クライアント SDK、Claude Agent SDK などがあり、名前が似ていて混乱しやすいところです。この章では、それぞれが何で、どう重なっているのかを図で整理し、そのあとで Messages API を使うときにつまずきやすい点をまとめます。

試験との関係：「アプリケーションと統合」（Claude API の仕組み）、「モデル選択と最適化」（SDK と API）、「エージェントとワークフロー」（Claude でエージェントを作る）にまたがります。「この場面では何を使うか」「このリクエストのどこが誤りか」を問う問題の土台です。根拠は Anthropic の公式ドキュメントです。

全体の地図：最後はすべて Messages API

まず押さえたいのは、どの方法を使っても、最後は同じ Messages API（POST /v1/messages）を通って Claude に届くということです。違いは、「その手前で、どこまでを用意してくれるか」です。

どこまで用意してくれるか

4つの違いは、「自分で書く部分」と「用意されている部分」の割合で比べると分かりやすくなります。下に行くほど、用意されている部分が増えます。

Agent SDK と Claude Code の関係：Agent SDK は、Claude Code を部品（ライブラリ）にしたものです。中では Claude Code と同じエンジン（エージェントのループ、ファイル操作やコマンド実行などの組み込みツール、権限、フック、サブエージェント）が動きます。人がターミナルの画面から使うのが Claude Code、自分のプログラムから使うのが Agent SDK です。

① Messages API（生の HTTP）

Messages API は、Claude と話すための窓口です。決まった URL に、決まった形の JSON を POST で送ると、Claude の返事が JSON で返ってきます。

curl https://api.anthropic.com/v1/messages \
  -H "x-api-key: $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -H "content-type: application/json" \
  -d '{
    "model": "claude-sonnet-5-5",
    "max_tokens": 1024,
    "messages": [{"role": "user", "content": "日本の首都はどこですか？"}]
  }'
  • ヘッダーで、API キー（x-api-key）、API の版（anthropic-version）、データの形式を伝える。
  • ボディの model・max_tokens・messages は必須。
  • エラーが出たときの再試行や、ストリーミングのイベントの読み取りも、すべて自分で書く。

HTTP やステータスコードの基本は はじめに「Web のしくみ」、リクエストの形の詳しい説明は Messages API 解説 にあります。

② クライアント SDK

SDK（Software Development Kit）は、Messages API をプログラミング言語から使いやすくした部品です。中でやっていることは、①と同じ HTTP のリクエストです。

from anthropic import Anthropic

client = Anthropic()   # API キーは環境変数 ANTHROPIC_API_KEY から自動で読む
message = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "日本の首都はどこですか？"}],
)
print(message.content[0].text)
SDK が用意してくれるもの内容
認証環境変数から API キーを読み、ヘッダーに付ける
再試行429 や 5xx、接続のエラーを、既定で2回自動で再試行する
タイムアウト既定のタイムアウトがあり、変更できる
型リクエストとレスポンスの形が型で決まっていて、書き間違いに気づきやすい
ストリーミングSSE のイベントを読み取り、最後に全体の返事をまとめて受け取る補助
エラーの種類レート制限、認証の失敗などを、種類ごとの例外として受け取れる
Tool Runner（beta）自分で定義したツールについて、「呼ぶ → 実行 → 結果を返す」のループを回してくれる補助
  • 公式の SDK は、Python・TypeScript（JavaScript）・Java・Go・Ruby・C#・PHP などがあります。
  • SDK の再試行の上に、自分でも無制限の再試行を重ねないこと。回数を要件に合わせて設定し、最後まで失敗したときの処理を書きます（→ SDK と API）。
  • Amazon Bedrock・Google Cloud の Vertex AI・Microsoft Foundry のようなクラウドから使うときも、同じ形のリクエストを、各クラウド用のクライアントから送ります（→ サードパーティのクラウドから使う）。

Tool Runner と Agent SDK は別物：Tool Runner は、ふつうの SDK の中にある補助で、自分で定義したツールのループを回すだけです。ファイル操作やコマンド実行のような組み込みツールはありません。Agent SDK は、組み込みツールも含めた Claude Code の仕組みまるごとです。

③ Claude Agent SDK

Claude Agent SDK は、Claude Code を、自分のプログラムの部品（ライブラリ）として使えるようにしたものです（Python 用と TypeScript 用があります）。中では Claude Code と同じエンジンが動きます。依頼の文章と設定を渡すと、エージェントのループを回し、ファイルを読み、コマンドを実行して、仕事を進めます。

# Claude Agent SDK のイメージ（Python）
async for message in query(
    prompt="tests フォルダのテストを実行して、失敗しているものを直して",
    options=ClaudeAgentOptions(allowed_tools=["Read", "Edit", "Bash"]),
):
    print(message)
用意されているもの内容
エージェントのループClaude の返事 → ツールの実行 → 結果を返す、を仕事が終わるまで繰り返す
組み込みツールファイルの読み書き・編集（Read・Write・Edit）、コマンド実行（Bash）、検索（Glob・Grep）、Web 検索・取得など
権限とフック使ってよいツールの指定、実行前後に必ず動く処理。Claude Code と同じ考え方
サブエージェント・MCP役割を分けた子のエージェント、MCP サーバーのツール
コンテキストの管理長くなった会話の整理など

自分の環境（自分のサーバー、CI など）で動かします。実行環境の運用は自分で行います。詳しくは Claude でエージェントを作る にあります。

参考：Anthropic がホストする方式：エージェントのループだけでなく、ツールを動かす実行環境まで Anthropic に任せる方式（Managed Agents、beta）もあります。Agent SDK は「仕組みだけ。動かす場所は自分」、こちらは「仕組みも動かす場所も Anthropic」です。セルフホストとの違いは デプロイの方式 を見てください。

④ Claude Code

Claude Code は、ターミナルや IDE で動く開発用のアプリです。人が指示し、Claude がリポジトリのコードを読み、編集し、コマンドを実行します。決まりは CLAUDE.md に、権限は settings.json に書きます（→ Claude Code の設定と権限）。CI から使うときは、ヘッドレスモード（claude -p）で1回の指示を実行させます。

Messages API でつまずきやすい点

ここからは、Messages API（SDK を使う場合も同じ）を使うときに、エラーや思わぬ動きの原因になりやすい点です。試験では「このリクエストの誤りはどれか」の形でよく出ます。

1. 会話は毎回すべて送り直す

Messages API は前の会話を覚えていません（ステートレス）。会話を続けるには、それまでのやり取りをすべて messages に入れて送ります。

最後の質問だけを送ると、「その」「さっきの」が何を指すか分からない返事になります。履歴が長くなったら、要約する・古いものを外すなどで整理し、同じ前置きにはプロンプトキャッシュを使います（→ ステートレス）。

2. 返事の content は丸ごと戻す

Claude の返事の content は、ブロックの配列です。文章（text）だけでなく、ツールを使いたいという依頼（tool_use）や、思考（thinking）のブロックが入っていることがあります。次のリクエストでは、受け取った content を丸ごと、そのまま assistant のメッセージとして戻します。

  • 文章だけ取り出して戻すのはだめ：tool_use のブロックが消えると、次の tool_result がどの依頼への答えか分からず、400 エラーになります。
  • thinking のブロックは中身を変えずに返す：書き換えると 400 になります。
  • 迷ったら「返ってきた content を、そのまま assistant として足す」と覚えます。

3. tool_result の置き場所と数

ルール守らないと
tool_use を含む assistant メッセージの直後の user メッセージに置く400（tool_use に対応する結果がない）
user の content の先頭に置く。文章を添えるなら tool_result の後ろ400
tool_use が複数なら、1つの user メッセージに、それぞれの tool_result を入れる400、または並列でツールを呼ばなくなる
tool_use_id で、どの依頼への結果かを対応づける400
ツールが失敗しても、is_error: true を付けて結果を返す結果がないので 400。Claude が失敗を知って対応できない

ツールを実行するのはアプリです。Claude は「このツールをこの入力で使いたい」と返すだけです（→ ツール利用のループ）。

4. そのほかのつまずきやすい点

つまずき正しくは
max_tokens を書き忘れるmodel・max_tokens・messages は必須。抜けると 400
全体の役割や方針を、毎回の user メッセージに混ぜる会話全体の方針はトップレベルの system に書く
返事の最後に assistant を置いて、続きを書かせる（プリフィル）最近のモデルでは 400。出力の形を決めたいなら構造化出力を使う
返事が途中で切れているのに気づかないstop_reason を確かめる。max_tokens なら上限で切れている
JSON で答えさせ、そのまま読む構造化出力で形を決め、受け取ったら検証する
400 のエラーを何度も再試行する400 はリクエストの誤り。直さない限り同じ。再試行するのは 429・500・529 など
API キーをブラウザの JavaScript に書くキーはサーバー側で、環境変数などから使う
Message Batches の結果を、送った順番どおりに読む順番は保証されない。custom_id で対応づける

エラーの種類と再試行は エラーと再試行、実際にわざと誤ったリクエストを送ってエラーを見るなら 疑似環境 で試せます。

この章のまとめ

  • どの方法も、最後は Messages API（POST /v1/messages）を通って Claude に届く。違いは、手前でどこまで用意してくれるか。
  • 生の HTTP → すべて自分。クライアント SDK → 認証・再試行・型・ストリーミングの補助。Claude Agent SDK → さらにエージェントのループと組み込みツール。Claude Code → アプリとして全部入り。
  • Agent SDK は Claude Code を部品（ライブラリ）にしたもの。中では同じ Claude Code のエンジンが動く。Tool Runner（SDK の補助）とは別物。
  • API は会話を覚えていない。毎回すべて送り直す。
  • 返事の content は丸ごと、そのまま戻す。tool_result は直後の user の先頭に、tool_use の数だけ、失敗も is_error で返す。
  • model・max_tokens・messages は必須。方針は system。途中で切れたら stop_reason を見る。400 は再試行しても直らない。
