はじめに：前提知識 第0章

CCDV-F は「Claude を使ってアプリを作る開発者」のための試験です。この章は、Web アプリを作ったことがない人が、ほかの章を読めるようになるための準備です。試験の配点はありませんが、すべての章の土台になります。

読み終えたとき、次のことを自分の言葉で説明できれば十分です。すでに知っている節は読み飛ばしてかまいません。

  1. claude.ai で Claude と話すことと、API で Claude を使うことの違い
  2. Web の通信は「リクエスト」と「レスポンス」の1往復であること。GET と POST、ステータスコード、ストリーミング
  3. JSON と JSON Schema の読み方
  4. API キーの扱い方と、認証・認可の違い
  5. Claude の API に何を送ると、何が返ってくるか
  6. トークン、コンテキスト、ツール利用の流れ
  7. Python のコード、ターミナルのコマンド、Git のリポジトリを読めること

Claude の2つの使い方

Claude は、Anthropic という会社が作った AI（大規模言語モデル）です。使い方は大きく2つあります。

A. 画面から使うB. API で組み込む
例claude.ai のチャット、デスクトップアプリ社内ヘルプデスクのボット、メールの自動分類、問い合わせの返信の下書き
使う人あなた自身あなたが作ったアプリの利用者
何を送るかあなたが入力した文章アプリ（プログラム）が組み立てた文章とデータ
返事をどう使うかあなたが読むアプリが画面に出す・データベースに保存する・次の処理に渡す

CCDV-F が問うのは、主に B の使い方です。「アプリが Claude に何を送り、返ってきたものをどう扱うか」を設計し、作り、運用できるかが試されます。

LLM
Large Language Model（大規模言語モデル）。大量の文章から学習し、文章を読んで続きの文章を作る AI。Claude は LLM の1つです。
API
Application Programming Interface。プログラムから、別のサービスの機能を呼び出すための窓口です。人が画面を操作する代わりに、プログラムが決まった形式でお願いを送ります。
アプリ（アプリケーション）
利用者が使うプログラム。この試験では、Claude を組み込んだ自社のサービスや社内ツールを指します。

API をレストランにたとえると、次のようになります。

たとえ：API はレストランの「注文票」

  • お客さん（アプリ）は、厨房（Claude）に直接入れません。
  • 決まった書式の注文票（API のリクエスト）に「何を・どれだけ」を書いて渡します。
  • 厨房は料理（レスポンス）を返します。書式が間違っていれば「この注文は受けられません」（エラー）と返ってきます。
  • 注文票の書式は店が決めています。API の書式は Anthropic が決め、公式ドキュメントで公開しています。

Web のしくみ：リクエストとレスポンス

Web の通信は、いつも「お願い」と「返事」の1往復です。ブラウザで Web ページを開くときも、アプリが Claude を呼ぶときも同じです。

クライアント
お願いを送る側。ブラウザや、あなたが作るアプリ。
サーバー
お願いに応える側。Claude の場合は Anthropic のコンピューター。
HTTP
クライアントとサーバーがやり取りするときの決まり（プロトコル）。暗号化したものを HTTPS といいます。
リクエスト
クライアントからサーバーへのお願い。
レスポンス
サーバーからクライアントへの返事。
URL
お願いの宛先。例：https://api.anthropic.com/v1/messages（Anthropic の API の、メッセージを作る窓口）。

リクエストとレスポンスは、どちらも次の部品でできています。

部品リクエストではレスポンスでは
1行目メソッドと URL（何を・どこに）ステータスコード（成功か失敗か）
ヘッダー付帯情報。API キー、データの形式など付帯情報。リクエストの ID、制限の残りなど
ボディ送るデータの中身（JSON など）返事の中身（JSON など）

手紙にたとえると、1行目とヘッダーが「封筒の表書き」、ボディが「便せんの中身」です。実際に流れている文字は、次のような形をしています。

実物の形：Claude に質問するリクエスト（アプリ → Anthropic）

POST /v1/messages HTTP/1.1                    ← 1行目：メソッドと宛先
Host: api.anthropic.com                       ← ヘッダー（ここから空行まで）
x-api-key: sk-ant-api03-DUMMYk3Jd9...
anthropic-version: 2026-10-21
content-type: application/json
                                              ← 空行で区切る
{                                             ← ボディ（送るデータ）
  "model": "claude-sonnet-5-5",
  "max_tokens": 300,
  "messages": [{"role": "user", "content": "日本の首都はどこですか？"}]
}

実物の形：返ってくるレスポンス（Anthropic → アプリ）

HTTP/1.1 200 OK                               ← 1行目：ステータス
content-type: application/json                ← ヘッダー
request-id: req_011DUMMY...

{                                             ← ボディ（返事の中身）
  "role": "assistant",
  "content": [{"type": "text", "text": "日本の首都は東京です。"}],
  "stop_reason": "end_turn",
  ...
}

ふだんは SDK やライブラリがこの文字の組み立てと読み取りをしてくれるので、開発者が直接書くことはほとんどありません。ただ、エラーの調査では「どのヘッダーに何が入っていたか」「ステータスはいくつか」を読む力が必要になります。

メソッド：GET と POST

メソッドは、サーバーに「何をしてほしいか」の種類です。よく使うのは次の2つです。

メソッド意味身近な例Claude の API での例
GET情報を取得する。ボディは送らないブラウザで Web ページを開く預けた一括処理（バッチ）の進み具合を確認する：GET /v1/messages/batches/{ID}
POSTデータを送って処理してもらう。ボディに中身を入れるフォームに入力して送信するClaude に文章を送って返事をもらう：POST /v1/messages

Claude に返事を書いてもらうときは、質問の文章（データ）を送る必要があるので POST を使います。ほかに PUT（置き換え）、DELETE（削除）などもありますが、この試験で意識するのは主に GET と POST です。

ステータスコード：結果を表す3桁の数字

コード意味たとえどうするか
200成功注文どおりの料理が来た結果を使う
400リクエストの書き方の誤り注文票の書き方が間違っている直してから送り直す
401認証の失敗（API キーの誤り）会員証が無効API キーを確認する
429送りすぎ（回数や量の上限を超えた）注文が多すぎて受付停止中少し待ってから送り直す
500 台サーバー側の問題・混雑厨房のトラブル少し待ってから送り直す

覚え方：2 で始まれば成功、4 で始まればこちらの誤り、5 で始まれば相手側の問題。429 だけは例外的に「待てば通る」4 台です。

返事を少しずつ受け取る：ストリーミング

ふつうの HTTP は「リクエスト1つに、レスポンス1つ」です。Claude の返事が長いと、全部できあがるまで何秒も待つことになります。そこで、リクエストに "stream": true を付けると、返事をできた部分から少しずつ受け取れます。これをストリーミングといいます。

実物の形：ストリーミングで届くデータ（SSE。一部を省略）

event: message_start
data: {"type":"message_start","message":{"role":"assistant","content":[], ...}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"日本の"}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"首都は東京です。"}}

event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"end_turn"},"usage":{"output_tokens":12}}

event: message_stop
data: {"type":"message_stop"}
  • 1つのレスポンスの中で、event:（出来事の名前）と data:（中身の JSON）の組が、次々に届きます。この形式を SSE（Server-Sent Events：サーバーから順に送られるイベント）といいます。
  • content_block_delta の text をつなげると、返事の全文になります（「日本の」＋「首都は東京です。」）。チャット画面で文字が流れるように表示されるのは、このためです。
  • 返事が終わった理由（stop_reason）は、最後のほうの message_delta で届きます。

なお、音声の会話のように「双方が同時に送り合う」通信には WebSocket という別の方式が使われることもあります。SSE はサーバーから一方向に送る方式です。

サーバーはどこにある？：ローカル・クラウド・ホスト

後の章では「セルフホスト」「リモート」「クラウド経由」といった言葉が出てきます。どれも「プログラムがどこで動いているか」を表す言葉です。

言葉意味例
ローカル自分のパソコンの中開発中に自分のパソコンでアプリを動かす
リモートネットワークの向こうにある別のコンピューターAnthropic の API、社内のサーバー
クラウドインターネット越しに借りて使うコンピューターやサービスAWS（Amazon）、Google Cloud、Microsoft Azure
ホスト（する）プログラムを動かし、運用すること。またはその場所「Anthropic がホストする」＝ Anthropic のコンピューターで動かしてもらう
セルフホスト自社が用意した環境で動かすこと自社のクラウドの中でエージェントを動かす
エンドポイントAPI の宛先の URLhttps://api.anthropic.com/v1/messages

Claude は Anthropic の API のほか、Amazon Bedrock（AWS）や Vertex AI（Google Cloud）など、クラウドの会社のサービスからも呼べます。同じ Claude でも、エンドポイントと認証の方法が変わります。

JSON の読み方

Claude の API では、送るデータも返ってくるデータも JSON（ジェイソン）という書き方を使います。人にも読めて、プログラムでも扱いやすい形式です。

サンプル：社員の情報を JSON で書く

{
  "name": "山田 花子",
  "age": 29,
  "remote": true,
  "skills": ["Python", "SQL"],
  "manager": {"name": "佐藤 一郎", "id": "E0012"},
  "phone": null
}
書き方呼び方意味サンプルの例
{ }オブジェクト「名前: 値」の組をまとめたもの全体、manager
"name": …キーと値左が項目の名前（キー）、右がその値"age": 29
"…"文字列文字。必ず " で囲む"山田 花子"
29数値数。" で囲まない29
true／false真偽値はい／いいえtrue
[ ]配列値を順番に並べたもの["Python", "SQL"]
nullnull値がない"phone": null

オブジェクトの中にオブジェクトや配列を入れられます（入れ子）。manager の name は「佐藤 一郎」、skills の1つめは「Python」と読みます。

プログラムで JSON から値を取り出す（Python）

import json

text = '{"name": "山田 花子", "skills": ["Python", "SQL"], "manager": {"name": "佐藤 一郎"}}'
data = json.loads(text)          # JSON の文字列を、プログラムで扱える形に変換

print(data["name"])              # → 山田 花子
print(data["skills"][0])         # → Python   （配列の番号は 0 から数える）
print(data["manager"]["name"])   # → 佐藤 一郎 （入れ子は [ ] を続けて書く）
print(len(data["skills"]))       # → 2        （配列の要素の数）

Claude の返事を取り出す message.content[0].text も、同じ考え方です。「content 配列の 0 番目の text」と読みます。

よくある書き間違い（エラーになる JSON）

{'name': '山田'}            ✕ 文字列は " で囲む（' は使えない）
{"name": "山田",}          ✕ 最後の要素の後ろに , を付けない
{"age": "29"}              △ エラーにはならないが、数値ではなく文字列になる
{"name": "山田"}           ◯

練習：次の JSON から「1つめのメッセージの役割」と「その文章」を読み取ってください

{
  "model": "claude-sonnet-5-5",
  "messages": [
    {"role": "user", "content": "こんにちは"}
  ]
}

答え：messages は配列で、その1つめ（messages[0]）の role は "user"（利用者）、content は "こんにちは" です。これが、Claude に送るリクエストの中心部分です。

JSON Schema：データの形の設計図

JSON は自由に書けるので、「どんな項目が、どんな型で入るか」を別に決めておかないと、受け取る側のプログラムが困ります。その形の決まりを書くための書き方が JSON Schema（ジェイソン・スキーマ）です。Claude に道具（ツール）を渡すときや、返事の形を決めるとき（構造化出力）に使います。

サンプル：「注文番号を1つ受け取る」という形の決まり

{
  "type": "object",                         ← 全体はオブジェクト { }
  "properties": {                           ← 中に入る項目の一覧
    "order_id": {
      "type": "string",                     ← 文字列（"A-00123" のように先頭の 0 も残る）
      "description": "注文番号。例：A-00123"
    },
    "include_items": {"type": "boolean"}    ← true / false
  },
  "required": ["order_id"],                 ← order_id は必ず入れる
  "additionalProperties": false             ← 決めた項目以外は入れない
}

この決まりに合うデータの例：{"order_id": "A-00123", "include_items": true}。
合わないデータの例：{"include_items": true}（必須の order_id がない）、{"order_id": 123}（文字列ではなく数値）。

よく使う指定意味
type型。object・string・number・integer・boolean・array
propertiesオブジェクトに入る項目と、それぞれの形
required必ず入れる項目
enum決まった候補の中からしか選べない。例：{"type": "string", "enum": ["請求", "配送", "返品"]}
items配列の1つ1つの要素の形
descriptionその項目の説明。Claude はこれを読んで、何を入れるかを判断する

API キー：アプリの「合鍵」

API キーは、「このリクエストは誰（どの会社のアカウント）からのものか」を Anthropic に示すための、長い文字列です。まずは実物のイメージを見てください。

API キーの見た目（ダミー。実際には使えません）

sk-ant-api03-DUMMYk3Jd9xQ2mVb7Lr0Tz5WcY8hN1pE4sA6uG...（実際は 100 文字ほど続く）
  • Anthropic の API キーは sk-ant- で始まる、ランダムな英数字の長い文字列です。
  • Anthropic のコンソール（開発者向けの管理画面）で発行します。発行した直後に一度だけ全体が表示されるので、その場で安全な場所に保存します。
  • このキーを持っている人は、誰でもあなたの会社のアカウントで Claude を使えます。料金も会社に請求されます。パスワードと同じ扱いです。

キーはリクエストのどこに入るか

キーは、リクエストのヘッダーの x-api-key に入れて送ります。ボディ（質問の中身）とは別の場所です。

リクエストの中のキーの位置

POST /v1/messages HTTP/1.1
Host: api.anthropic.com
x-api-key: sk-ant-api03-DUMMYk3Jd9xQ2mVb7Lr0Tz5WcY8hN1pE4sA6uG...   ← ここ
anthropic-version: 2026-10-21
content-type: application/json

{"model": "claude-sonnet-5-5", "max_tokens": 300, "messages": [...]}

キーが間違っている・無効になっている場合は、ステータス 401（認証の失敗）が返ってきます。

やってはいけない置き方

✕ 悪い例：コードにキーを直接書く（app.py）

from anthropic import Anthropic

client = Anthropic(api_key="sk-ant-api03-DUMMYk3Jd9xQ2mVb7Lr0Tz5WcY8hN1pE4sA6uG...")  # ✕

このファイルを Git で共有すると、リポジトリを見られる全員がキーを手に入れます。公開リポジトリなら世界中から見えます。後でキーの行を消しても、Git の履歴には残り続けます。

✕ 悪い例：ブラウザで動く JavaScript にキーを入れる

// Web ページの中の script（利用者のブラウザで動く）
fetch("https://api.anthropic.com/v1/messages", {
  method: "POST",
  headers: { "x-api-key": "sk-ant-api03-DUMMYk3Jd9..." },   // ✕ 誰でも見られる
  body: JSON.stringify({ /* ... */ })
});

ブラウザで動くプログラムは、利用者が開発者ツールで中身を自由に見られます。スマートフォンのアプリに埋め込んだ場合も、アプリを解析すれば取り出せます。

正しい置き方：環境変数から読む

環境変数とは、プログラムの外（OS やサーバーの設定）からプログラムに渡す値のことです。コードにはキーそのものを書かず、「ANTHROPIC_API_KEY という名前の値を読む」とだけ書きます。

◯ 手順1：自分のパソコンで試すとき（ターミナル）

# ターミナルで、環境変数にキーを入れる（このウィンドウを閉じると消える）
export ANTHROPIC_API_KEY="sk-ant-api03-DUMMYk3Jd9xQ2mVb7Lr0Tz5WcY8hN1pE4sA6uG..."

# 入ったか確認する（先頭だけ表示して、全体は画面に出さない）
echo ${ANTHROPIC_API_KEY:0:10}
# → sk-ant-api

◯ 手順2：コードはキーを知らないまま書く（app.py）

import os
from anthropic import Anthropic

# 書き方A：SDK は環境変数 ANTHROPIC_API_KEY を自動で読む
client = Anthropic()

# 書き方B：自分で読む場合も、値そのものはコードに書かない
client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])

このコードは Git で共有しても安全です。キーはどこにも書かれていません。

◯ 手順3：設定ファイルにまとめる場合は、Git の対象から外す

# .env（キーを書いたファイル。自分のパソコンにだけ置く）
ANTHROPIC_API_KEY=sk-ant-api03-DUMMYk3Jd9xQ2mVb7Lr0Tz5WcY8hN1pE4sA6uG...

# .gitignore（Git に含めないファイルの一覧）
.env

.env のような設定ファイルを使うときは、必ず .gitignore に書いて、Git で共有されないようにします。本番のサーバーでは、クラウドのシークレット管理の仕組み（AWS Secrets Manager など）にキーを保管し、そこから環境変数として渡すのが一般的です。

キーを守るつなぎ方

キーを利用者に渡さないために、Claude を呼ぶのは自社のサーバーのプログラムにします。

利用者 → 自社のサーバー → Claude の順につなぐ

[利用者のブラウザ]                [自社のサーバー]                     [Claude の API]
  POST /api/ask           →      キーを環境変数から読み、       →    POST /v1/messages
  {"question": "…"}               Claude へのリクエストを作る          x-api-key: sk-ant-…
                         ←      返事の文章だけを返す           ←    {"content": [...]}
  （キーは一度も通らない）

ブラウザは自社のサーバーとしか話しません。キーはサーバーの中だけにあり、利用者の目には触れません（最初の図の B の形です）。

漏れてしまったら：すぐにコンソールでそのキーを無効にし、新しいキーを発行して差し替えます。消しただけでは不十分です（Git の履歴や、誰かの手元に残っている可能性があるため）。キーは用途や環境（開発用・本番用）ごとに分けて発行しておくと、無効にしたときの影響を小さくできます。

認証と認可：「誰か」と「何をしてよいか」

セキュリティの章でよく出てくる2つの言葉です。似ていますが、確かめることが違います。

言葉確かめること身近な例Claude のアプリでの例
認証（authentication）相手が誰か社員証で本人だと確かめるAPI キーで「どの会社のアプリか」を確かめる。利用者のログイン
認可（authorization）その人が何をしてよいか社員証で入れる部屋が決まっているログインした利用者が、自分の注文だけを見られる

例：注文の問い合わせボットで、何をどこで確かめるか

利用者がログイン            → 認証（アプリ）：この人は山田さん
「私の注文はいつ届く？」    → 認可（アプリ）：山田さんが見てよいのは山田さんの注文だけ
                              → 山田さんの注文だけをデータベースから取り出す
アプリが Claude を呼ぶ      → 認証（Anthropic）：API キーで、この会社のアプリだと確かめる
Claude が返事を書く         → 渡されたのは山田さんの注文だけなので、他人の注文は答えようがない

大切なのは、認可を Claude の判断に任せないことです。「他人の注文は答えないで」とプロンプトに書いても、強制力はありません。見てよいデータだけをアプリが選んで渡します。必要な権限だけを与えることを最小権限（least privilege）といいます。

Claude の API を呼んでみる

ここまでの部品を組み合わせると、Claude の API の呼び出しが読めるようになります。

サンプル1：コマンド（curl）で呼ぶ

curl https://api.anthropic.com/v1/messages \
  -H "x-api-key: $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -H "content-type: application/json" \
  -d '{
    "model": "claude-sonnet-5-5",
    "max_tokens": 300,
    "messages": [
      {"role": "user", "content": "日本の首都はどこですか？"}
    ]
  }'
  • curl：コマンドから HTTP のリクエストを送る道具。-d でボディを付けると、POST で送られます。
  • -H：ヘッダー。API キー、API の版（anthropic-version）、データの形式（JSON）を伝えます。
  • $ANTHROPIC_API_KEY：環境変数に入れた API キー。コマンドに直接書きません。
  • ボディの model（どのモデルか）・max_tokens（返事の長さの上限）・messages（会話）の3つは必須です。

サンプル2：返ってくるレスポンス（ステータス 200）

{
  "id": "msg_01...",
  "type": "message",
  "role": "assistant",
  "model": "claude-sonnet-5-5",
  "content": [
    {"type": "text", "text": "日本の首都は東京です。"}
  ],
  "stop_reason": "end_turn",
  "usage": {"input_tokens": 18, "output_tokens": 12}
}
  • role: "assistant"：Claude からの返事であること。
  • content：返事の本文。配列になっていて、文章は content[0].text に入っています。
  • stop_reason：返事が終わった理由。end_turn は「書き終えた」。max_tokens なら上限で途中で切れています。
  • usage：使ったトークンの数。料金の計算に使います。

サンプル3：同じことを Python の SDK で書く

from anthropic import Anthropic

client = Anthropic()   # API キーは環境変数 ANTHROPIC_API_KEY から自動で読む

message = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=300,
    messages=[{"role": "user", "content": "日本の首都はどこですか？"}],
)
print(message.content[0].text)   # → 日本の首都は東京です。

SDK（Software Development Kit）は、API を各言語から呼びやすくした部品集です。中では同じ POST のリクエストを送っていますが、ヘッダーの付け方やエラー時の再試行を代わりにやってくれます。実際の開発では SDK を使うのが普通です。

試してみる 本物の API キーがなくても、Messages API 疑似環境で、リクエストを書き換えてレスポンスやエラーの変化を確かめられます。

LLM の基本：トークン・コンテキスト・ツール

トークン

Claude は文章をトークンという小さな単位に区切って読み書きします。おおよそ単語や文字のかたまりで、日本語は英語より多くのトークンになりやすい傾向があります。

  • 料金は「読んだトークン数（入力）」と「書いたトークン数（出力）」で決まります。出力の方が単価が高めです。
  • 上限もトークンで決まります。max_tokens は返事の長さの上限、コンテキストウィンドウは1回に扱える量（入力と出力の合計）の上限です。

Claude は前の会話を覚えていない

API は、1回1回のリクエストを独立したものとして扱います（ステートレス）。会話を続けるには、それまでのやり取りを毎回すべて送り直します。

サンプル：2回目のリクエスト（1回目のやり取りも含めて送る）

"messages": [
  {"role": "user",      "content": "日本の首都はどこですか？"},
  {"role": "assistant", "content": "日本の首都は東京です。"},
  {"role": "user",      "content": "その人口は？"}
]

「その」が東京を指すと分かるのは、1回目の質問と返事も一緒に送っているからです。3行目だけを送ると、Claude には何の人口か分かりません。会話が長くなるほど送るトークンが増え、料金も時間も増えます。

role（役割）
user は利用者（アプリ）からの発言、assistant は Claude の発言。
プロンプト
Claude に渡す指示や質問の文章のこと。
system プロンプト
会話全体に効く前提や役割の指示。messages とは別の system 項目に書きます。

返事は毎回少し変わる

LLM は、次に来そうな言葉を確率にもとづいて選びながら文章を作ります。そのため、同じ質問でも返事の言い回しが毎回少し変わることがあります。プログラムで扱うときは、出力の形を決める（構造化出力）、出力を検証する、といった工夫をします。これは後の章で詳しく学びます。

また LLM は、もっともらしいが事実と違う内容を、自信ありげに書いてしまうことがあります。これをハルシネーション（hallucination）といいます。重要な内容は、根拠を示させたり、元のデータと照合したりして確かめます。

コンテキスト：1回に渡す情報のすべて

コンテキストとは、1回の呼び出しで Claude が読む情報の全体のことです。後の章で「コンテキストが膨らむ」「コンテキストを分ける」と出てきたら、この箱の中身の話です。

1回のリクエストのコンテキストに入るもの

コンテキスト（上限＝コンテキストウィンドウ）
├─ system     役割や方針の指示
├─ tools      使ってよい道具の一覧と説明
├─ messages   これまでの会話（質問・返事・道具の結果）と、渡した資料
│    …ここまでが入力…
└─ 出力       Claude の返事

入れるほど料金が上がり、遅くなり、大事な情報が埋もれやすくなります。「何でも入れる」ではなく「必要なものを選んで入れる」のが基本です。

ツール利用とエージェントの考え方

Claude は文章を書くことしかできません。データベースを調べたり、メールを送ったりはできません。そこで、アプリがツール（Claude に使わせる道具。中身はアプリの関数）を用意します。流れは次のとおりです。ツールを実行するのは Claude ではなくアプリである点が大切です。

サンプル：「注文 A-00123 はいつ届く？」に答えるまで

① アプリ → Claude：質問と、ツールの一覧を送る
   "tools": [{"name": "get_order_status", "description": "注文の配送状況を返す",
              "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}},
                               "required": ["order_id"]}}]

② Claude → アプリ：「このツールをこの入力で使いたい」と返す（stop_reason: "tool_use"）
   {"type": "tool_use", "id": "toolu_01...", "name": "get_order_status",
    "input": {"order_id": "A-00123"}}

③ アプリ：自分の関数 get_order_status("A-00123") を実行する
   → {"status": "配送中", "eta": "11月25日"}

④ アプリ → Claude：①②の会話に、ツールの結果（tool_result）を足して送り直す
   {"type": "tool_result", "tool_use_id": "toolu_01...", "content": "{\"status\": \"配送中\", ...}"}

⑤ Claude → アプリ：「ご注文 A-00123 は配送中で、11月25日に届く予定です。」（stop_reason: "end_turn"）

②〜④を、Claude がツールを使わなくなるまで繰り返すプログラムをエージェントと呼びます。次に何をするかを Claude が決めるので柔軟ですが、回数や費用が読みにくくなります。一方、手順をあらかじめプログラムで決めて順に呼び出す形をワークフローと呼びます。どちらを選ぶかは「エージェントとワークフロー」の章で学びます。

プログラムの読み方

後の章には、Python のコードや、コードに近い書き方（疑似コード）が出てきます。プログラムを書けなくても、何をしているかを読めると理解が進みます。よく出てくる形はこれだけです。

サンプル：よく出てくる形（Python）

# 「#」から後ろはコメント（説明のメモ）。プログラムとしては無視される

# 変数：値に名前を付けて入れておく箱
city = "東京"
count = 0

# 関数：入力（引数）を受け取り、結果を返す「部品」
def get_order_status(order_id):
    # if：条件によって処理を分ける
    if order_id == "":
        return {"error": "注文番号がありません"}
    return {"order_id": order_id, "status": "配送中"}

# リスト（JSON の配列と同じ）と、for：1つずつ繰り返す
orders = ["A-001", "A-002"]
for order in orders:
    result = get_order_status(order)   # 関数を呼び出し、結果を変数に入れる
    print(result["status"])            # → 配送中（2回表示される）

# while：条件が成り立つ間、繰り返す
while count < 3:
    count = count + 1                  # 3 になったら止まる

# try / except：失敗（例外）が起きたときの処理
try:
    number = int("abc")                # 文字を数値に変換しようとして失敗する
except ValueError:
    print("数値に変換できませんでした")
形意味後の章での使われ方
関数（def）入力を受け取り、結果を返す部品Claude に渡す「ツール」の中身は関数。Claude が使いたいと言った関数を、アプリが実行する
if条件で分ける「stop_reason が tool_use ならツールを実行する」
for／while繰り返すエージェントのループ（ツールを使い終わるまで繰り返す）。必ず上限を付ける
try／except失敗に備えるAPI のエラーやツールの失敗を受け止めて、再試行や報告をする
辞書 { }「名前: 値」の組（JSON のオブジェクトと同じ形）リクエストやレスポンスを組み立てる・読む

Python では、行の先頭の字下げ（インデント）で「どこまでが if の中か」「どこまでが関数の中か」を表します。字下げがそろった部分が、ひとまとまりです。

ターミナルとコマンド

ターミナルは、文字でコンピューターに命令（コマンド）を出す画面です。Mac では「ターミナル」、Windows では「PowerShell」などが使えます。Claude Code もターミナルで動きます。

コマンドの読み方

$ claude -p "この差分を要約して" --output-format json
部分呼び方意味
$プロンプト「ここからコマンドを入力する」という印。入力はしない
claudeコマンド実行するプログラムの名前（Claude Code）
-pオプション動き方の指定。ここでは「対話せずに1回だけ実行して、結果を出す」
"この差分を要約して"引数コマンドに渡す値。ここでは Claude への指示。空白を含むので " で囲む
--output-format jsonオプションとその値結果を JSON の形で出す

- や -- で始まるものがオプションです。-p のように1文字の短い形と、--output-format のように長い名前の形があります。

よく使うコマンド意味
pwd今いるフォルダ（ディレクトリ）を表示する
lsフォルダの中身を一覧する（ls -a で . で始まる隠しファイルも表示）
cd フォルダ名フォルダを移動する
cat ファイル名ファイルの中身を表示する
export 名前=値環境変数を設定する（Mac・Linux）
claudeClaude Code を起動する

ファイルの場所（パス）の書き方

Claude Code の設定ファイルの説明では、~/.claude/settings.json や ./CLAUDE.md のような書き方が出てきます。これをパスといい、ファイルの場所を表します。

書き方意味例
~自分のホームフォルダ（例：/Users/yamada）~/.claude/settings.json ＝ 自分専用の Claude Code の設定
./今いるフォルダ（多くはプロジェクトのフォルダ）./CLAUDE.md ＝ プロジェクトの直下の CLAUDE.md
/ で区切るフォルダの中のフォルダ.claude/skills/release/SKILL.md
. で始まる名前隠しファイル・隠しフォルダ（ふだんは表示されない）.claude/、.env、.gitignore

標準入力・標準出力とパイプ

コマンドは、文字を受け取り（標準入力）、文字を出します（標準出力）。|（パイプ）でつなぐと、前のコマンドの出力を、次のコマンドの入力として渡せます。

サンプル：ファイルの中身を Claude Code に渡して要約させる

$ cat meeting-notes.txt | claude -p "3行で要約して"
（cat の出力 ＝ 議事録の文章が、claude の入力になる）

この「標準入出力でやり取りする」しくみは、MCP の章の stdio という通信方式と同じ考え方です。アプリが MCP サーバーを自分のパソコンの中でプロセス（動いているプログラム）として起動し、標準入出力で JSON をやり取りします。

Git とリポジトリ

Git は、ファイルの変更の履歴を記録する道具です。「いつ・誰が・何を・なぜ変えたか」が残り、問題が起きたら前の状態に戻せます。プログラムだけでなく、プロンプトや設定ファイルも Git で管理するのが基本です。

リポジトリ
Git で管理しているフォルダ（プロジェクト一式）。
コミット
変更を、説明つきで履歴に記録すること。1つ1つの記録もコミットと呼びます。
GitHub
リポジトリをインターネット上で共有するサービス。チームで同じリポジトリを使えます。
ブランチ
本流に影響を与えずに作業するための枝分かれ。
プルリクエスト（PR）
「このブランチの変更を本流に入れてください」という依頼。ここでコードレビューを行います。
CI
Continuous Integration。変更を送るたびに、テストなどを自動で実行するしくみ（GitHub Actions など）。

サンプル：Claude を使うプロジェクトのリポジトリの中身

my-app/                        ← リポジトリ
├── CLAUDE.md                  ← Claude Code への決まり（チームで共有する）
├── .claude/
│   ├── settings.json          ← チームで共有する Claude Code の設定
│   ├── settings.local.json    ← 自分だけの設定（Git に入れない）
│   └── skills/release/SKILL.md ← チームの作業手順（スキル）
├── prompts/support_v3.md      ← プロンプトもファイルにして履歴を残す
├── src/app.py                 ← アプリのプログラム
├── tests/test_app.py          ← テスト
├── .gitignore                 ← Git に入れないファイルの一覧（.env など）
└── .env                       ← API キー（Git に入れない）

サンプル：よく使う Git のコマンド

$ git status                         # 変更したファイルを確認する
$ git diff                           # 何をどう変えたか（差分）を見る
$ git add prompts/support_v3.md      # 記録する対象に加える
$ git commit -m "返品の案内を追加"    # 説明をつけて履歴に記録する
$ git log --oneline                  # 履歴の一覧を見る
$ git push                           # GitHub に送って共有する

サンプル：CI の設定（プルリクエストのたびにテストを自動で実行する）

# .github/workflows/test.yml
on: pull_request                     # いつ動かすか：プルリクエストが作られたとき
jobs:
  test:
    runs-on: ubuntu-latest           # どこで動かすか：GitHub が用意するコンピューター
    steps:
      - uses: actions/checkout@v4    # リポジトリの中身を取ってくる
      - run: pip install -r requirements.txt
      - run: pytest                  # テストを実行する

この書き方は YAML（ヤムル）という設定ファイルの形式で、字下げで入れ子を表します。後の章で出てくる「CI で Claude Code を動かす」は、この run: の行で claude -p … を実行するイメージです。

この章のまとめ

  • CCDV-F の中心は、API で Claude を自分のアプリに組み込む使い方。
  • Web の通信はリクエストとレスポンスの1往復。Claude への質問は POST。結果はステータスコードで分かる（2 成功、4 こちらの誤り、5 相手側）。ストリーミングは返事を少しずつ受け取る。
  • データは JSON。形の決まりは JSON Schema（type・properties・required・enum）。
  • API キーはパスワードと同じ。コードやブラウザに置かず、サーバー側で環境変数などから使う。認可はアプリの仕組みで行い、Claude の判断に任せない。
  • 必須は model・max_tokens・messages。返事は content[0].text、終わった理由は stop_reason。
  • 料金と上限はトークンで決まる。API は会話を覚えていない。コンテキストは必要なものを選んで入れる。
  • ツールを実行するのはアプリ。ツールを使い終わるまで繰り返すのがエージェント。
  • 関数・if・ループ・try、コマンドとオプション、パス（~・./）、Git のコミットと CI が読めれば、後の章のサンプルを追える。
