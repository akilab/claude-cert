API の仕組み（要点）

詳しくは Messages API 解説 と疑似環境で学びます。ここでは試験で特に問われる判断をまとめます。

状況選ぶもの理由
利用者が画面で待つ。体感を速くしたいストリーミング最初の文字が早く出る。品質・料金は同じ
急がない大量処理。コスト最優先Message Batches API50% の料金。最長24時間
毎回同じ長い前置きを送っているプロンプトキャッシュ読み込みは入力の 0.1倍程度。速度も向上
出力を機械で読みたい構造化出力JSON スキーマで形を保証
社外にデータを出せない規定がある契約中のクラウド経由（Bedrock・Vertex AI など）同じ Claude を、自社のクラウド環境から使える

サードパーティのクラウドから使う

Claude は Anthropic の API のほか、Amazon Bedrock や Google Cloud の Vertex AI などからも使えます。既存のクラウド契約、請求のまとめ方、データの保存場所や社内の規定に合わせて選びます。呼び出し方（認証やエンドポイント、使える機能の時期）は提供元によって少し違うので、移行の際は確認が必要です。

アプリの設計（Claude Application Design）

このスキルは配点が最も大きく（8.6%）、「Claude をどう組み込むと、品質・安全・保守性が高くなるか」を問います。

インターフェースによる違い

インターフェース指示の入り口特徴
API／SDKsystem パラメータ、messages、toolsすべてをアプリが制御する。履歴の管理もアプリ
Claude CodeCLAUDE.md、settings.json、スラッシュコマンド、Skills、フックリポジトリの文脈で動くエージェント。ファイル操作やコマンド実行を行う
claude.ai／Desktopプロジェクトの指示、アップロードした資料、コネクタ人が対話的に使う。組織の設定で機能を管理

同じ「指示」でも、どこに書くかで効き方が変わります。全体の方針は system や CLAUDE.md に、その回の依頼は user に、が基本です。

コンテンツの境界（content boundaries）

指示（信頼できる）と、データ（利用者の入力・文書・Web ページなど、信頼できない）を、XML タグやブロックではっきり分けて渡します。境界が曖昧だと、データの中の命令に引きずられやすくなります（プロンプトインジェクション）。

スキーマ設計

  • 後続のシステムが読む出力は、構造化出力やツールの input_schema で形を決める。
  • 値の候補は enum で固定する（自由な文字列にしない）。
  • 受け取った後も、業務上ありえない値でないかをアプリで検証する。

セッションの衛生管理（session hygiene）

✕ 1つの会話に何でも詰め込む

  • 無関係な履歴で入力が膨らみ、遅く・高くなる
  • 前の話題が混ざる

◯ タスクごとに会話を分ける

  • 話題が変わったら新しいセッション
  • 必要なら要約だけを引き継ぐ
  • Claude Code では /clear や新しいセッションを使う

プラグインの管理

Claude Code などでは、コマンド・エージェント・Skills・フック・MCP の設定をまとめたプラグインで機能を配布できます。チームで使うプラグインは、出どころと権限を確認し、バージョンと依存関係を管理します（→ 構成管理）。

「インターフェースによって指示の置き場所が違う」「指示とデータの境界」「機械が読む出力はスキーマで」「タスクごとにセッションを分ける」が頻出。

ソフトウェア工学の基本

LLM の知識だけでなく、Web API を組み込む開発者としての基礎が問われます（7.4%）。

REST と HTTP

ステータス意味呼び出す側の対応
2xx成功結果を使う
4xx呼び出す側の誤り（入力・認証・権限・存在しない）直してから送る。再試行しても同じ
429回数・量の制限待って再試行
5xxサーバー側の障害待って再試行（上限つき）

自分で API を作るときも同じ考え方です。入力の誤りは 400 と分かりやすいメッセージで返し、外部の API（Claude）を呼ぶ前に検証して、無駄な呼び出しと費用を防ぎます。

非同期処理と並行実行

LLM の呼び出しは数秒かかるので、大量の処理を1件ずつ順番に行うと時間がかかります。

  • 非同期のクライアント（Python の AsyncAnthropic など）で並行に送る。
  • 同時に送る数をセマフォなどで制限し、レート制限を超えにくくする。
  • 429 や 529 は待って再試行する。
  • すぐに結果が要らないなら、Batches API に切り替える。

JSON

リクエストもレスポンスも JSON です。文字列のエスケープ、数値と文字列の違い（例："00123" と 123）、必須項目の欠落など、型の扱いの誤りは不具合の典型的な原因です。

バージョン管理・コードレビュー・リファクタリング

  • プロンプトや設定も、コードと同じく Git で管理し、レビューを通して変更する。
  • AI が書いたコードもレビューする。大きな変更は小さく分け、テストを成功基準にする。
  • 大規模なリファクタリング（例：古いフレームワークからの移行）は、計画 → 小さな単位で実行 → テスト、を繰り返す。Claude Code はこうした作業の支援に向いている。

構成管理

Claude を使うシステムの「設定」を、変更しやすく・追跡しやすく・戻しやすく管理します（4.1%）。

対象管理の方法
モデルバージョンを固定（pinning）。設定ファイルや環境変数に1か所で書く。切り替えは評価を通してから
プロンプトバージョン管理し、変更ごとに評価を実行。どの版で何が変わったかを追えるようにする
CLAUDE.mdプロジェクトの決まりをリポジトリで共有（→ CLAUDE.md の階層）
settings.jsonClaude Code の権限・フック・環境変数など。チーム共有用と個人用を分ける
プラグイン依存関係とバージョンを管理し、出どころを確認する
API キー・シークレットコードに書かず、シークレット管理の仕組みで扱う（→ キーの管理）
「モデルが更新されて出力が変わり、後続が壊れた」→ バージョン固定＋評価してから切り替え。「どの変更で品質が落ちたか分からない」→ プロンプトのバージョン管理＋変更ごとの評価。

要件の理解

ビジネスの要望を、測れる要件に言い換えます（3.4%）。

業務の言葉要件への言い換えの例
お客様を待たせたくない最初の文字まで2秒以内（ストリーミング、速いモデル）
個人情報を社外に保存しないデータの保存場所・保持期間、ログの伏せ字、提供元の選択
月の予算は○○円1件あたりの費用の上限、モデルの選択、キャッシュ・バッチの活用
間違いは困る評価の正答率の目標、人の確認、根拠の提示

機能要件（何をするか）と、非機能要件（速度・可用性・セキュリティ・コストなど、どのようにするか）を分けて整理し、設計の前に確定させます。

システムのライフサイクル

開発 → 導入 → 運用 → 保守、の全体を見通します（2.8%）。LLM のシステムは、モデルの更新や入力の傾向の変化で、コードを変えなくても挙動が変わる点が特徴です。

  • 導入：段階的に展開する（一部の利用者から始めるカナリアリリース）。切り戻しの手順を先に用意する。
  • 運用：エラー率・遅延・費用に加え、出力の品質を継続的に監視する。
  • 保守：モデルの提供終了に備えて移行を計画する。本番で見つかった失敗を評価データに加える。

この分野のまとめ

  • 状況に応じて、ストリーミング・Batches・キャッシュ・構造化出力を選べる。
  • 指示とデータの境界、スキーマ設計、セッションの分割。
  • 4xx は直す、429・5xx は待って再試行。並行処理は同時実行数を制限。
  • モデルの固定、プロンプトのバージョン管理、変更は評価を通して段階的に。
