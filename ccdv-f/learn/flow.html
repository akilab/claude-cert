開発の流れ（ディスカバリーから運用まで） 全分野

Claude を使ったアプリは、いきなりプロンプトを書くところからは始まりません。「何に困っているのか」を見つけるところ（ディスカバリー）から始まり、本番で動かし続けるところまでが1つの流れです。この章では、その流れを図で追います。

試験との関係：試験ガイドの「要件の理解（Understanding Requirements、3.4%）」と「システムのライフサイクル（Systems Life Cycle、2.8%）」が直接の範囲です。それに加えて、「どの段階で何をすべきか」を問う形で、設計・評価・デプロイメント・運用の問題にも広く関わります。

全体の流れ：8つの段階

家を建てるときを思い浮かべてください。いきなり柱を立てる人はいません。まず「誰が住み、何に困っているか」を聞き（①）、「部屋は3つ、予算はいくら」と条件を決め（②）、設計図を描き（③）、完成したら何を確かめるかを決めてから（④）建て始めます（⑤⑥）。引き渡したあとも点検と修理が続きます（⑦⑧）。アプリの開発も同じです。

ポイントは2つです。

  • ④ 評価の準備が、⑤ 実装より先にある：何ができたら合格かを先に決めておかないと、作ったものが良いのか判断できません。LLM のアプリでは特に大事な順番です。
  • ⑧で終わらず、輪になっている：LLM のアプリは、入力の傾向やモデルの更新で、コードを変えなくても品質が変わります。本番で見つけた失敗を④⑤に戻して直し続けます。

この章では、ネットショップの問い合わせメールを担当の窓口に振り分けるアプリを例に、8つの段階を順に見ていきます。評価（eval）とは何か で使った例と同じです。

① ディスカバリー：本当の課題を見つける

ディスカバリー（discovery）は「発見」という意味で、開発の最初に「誰が、何に、どれくらい困っているのか」を聞き出して、本当に解くべき課題を見つける段階です。日本語では「ヒアリング」「課題の発見」「現状の調査」などと呼ばれることもあります。

依頼する人は、困りごとではなく「解決策」の形で依頼してくることがよくあります。「なぜ？」を繰り返して、その奥にある課題を見つけます。

依頼どおりにチャットボットを作っていたら、お客様と会話する複雑な仕組みが必要になり、時間も費用もかかったはずです。課題が「振り分け」だと分かれば、メールを5種類に分類するだけの、ずっと単純なアプリで解決できます。

ディスカバリーで確かめる6つのこと

確かめること聞くことの例例のアプリでの答え
課題何に困っていますか。困ると何が起きますか振り分けに毎日3時間。返信が遅れて苦情が来る
人誰が使い、誰が決め、誰の確認が要りますか使う：窓口の担当者。決める：サポート部長。確認：情報システム部（個人情報）
今の流れ今はどんな手順ですか。件数と時間は1日300件。2人で読み、5つの窓口に転送している
データどんなデータがどこにありますか。機密度はメール本文（氏名・住所を含む）。過去1年分の振り分け結果が残っている
成功の指標何がどれだけ良くなれば成功ですか振り分けの時間をゼロに近づける。誤った振り分けは今（約5%）以下に
制約予算、期限、守るべき規則、つなぐシステムは月の予算は3万円。メール本文を社外のログに残さない。既存の受付システムにつなぐ

特に大事なのは成功の指標とデータです。成功の指標は、あとで④の評価の合格基準になります。データ（ここでは過去1年分の振り分け結果）は、そのまま④の評価データの材料になります。ディスカバリーで聞き漏らすと、後の段階で困ります。

そもそも LLM を使うべきか

ディスカバリーでは、LLM を使わずに済まないかも考えます。LLM は便利ですが、ふつうのプログラムより遅く、費用がかかり、出力がぶれます。

問い合わせメールは、同じ「返品したい」でも書き方が人によってばらばらです。キーワードの一致のような決まったルールでは振り分けきれないので、文の意味を読める LLM が向いています。

ディスカバリーのメモ（例）

  • 課題：問い合わせメール（1日約300件）を2人で読み、5つの窓口に振り分けている。毎日約3時間。返信の遅れで苦情が出ている。
  • 本当に必要なもの：会話するチャットボットではなく、メールの自動振り分け。
  • 成功の指標：振り分けの作業時間を1日30分以下に。誤った振り分けは今と同じ約5%以下。
  • データ：過去1年分のメールと振り分け結果（約7万件）。氏名・住所・電話番号を含む。
  • 制約：月3万円以内。メール本文を社外のログに残さない。3か月後に開始したい。
  • 関係者：サポート部長（決める）、窓口の担当者（使う）、情報システム部（個人情報の確認）。
「依頼された機能をそのまま作る」より「まず課題・利用者・成功の指標を確かめる」が正解になりやすい。「最初に何をすべきか」と問われたら、作り始める前に確かめることを選ぶ。

② 要件定義：「できた」を測れる条件にする

要件とは、アプリが満たすべき条件のことです。ディスカバリーで聞いた「困りごと」や「成功の指標」を、あとで「できた・できていない」を判定できる形に書き直します。

月3万円 ÷（1日300件 × 30日）＝ 1件あたり約3円

要件は2種類に分けて書きます。

機能要件：「何をするか」

  • メールを「配送」「返品・交換」「支払い」「苦情」「その他」に分類する
  • 分類に応じて、担当の窓口のキューに入れる
  • 判断できないものは人の確認に回す

非機能要件：「どのように」

  • 速さ：1件5秒以内
  • 品質：正答率95%以上
  • 費用：1件3円以下
  • 安全：メール本文を社外のログに残さない

非機能要件が決まると、③の設計で「どのモデルを使うか」「すぐに返すか、まとめて処理するか」を選べるようになります。例えば「5秒以内」「1件3円以下」なら、速くて安いモデルで足りるかを最初に試します。詳しくは アプリケーションと統合「要件の理解」 にあります。

「使いやすく」「高品質に」「なるべく速く」は要件として不十分。数字で測れる形に言い換えたものが正解になりやすい。

③ 設計：仕組みとモデルを決める

要件を満たすために、どんな部品を、どんな順番でつなぐかを決めます。家でいえば設計図です。

図のように、Claude に任せるのは「分類」の1か所だけです。署名の除去や、答えが5種類のどれかになっているかの確認は、ふつうのコードで確実に行います。設計で決めることは、主に次のとおりです。

決めること例のアプリでの決定理由（どの要件から来たか）
構成：ワークフローかエージェントか決まった順番で処理するワークフロー手順が毎回同じ。いちばん単純な方法で足りる
モデルまず速くて安いモデルで試す1件5秒以内・3円以下。足りなければ上位のモデルを評価する
出力の形5種類の選択肢に限った構造化出力後の処理（キューに入れる）が機械なので、形を決める
失敗したとき人の確認に回す。API のエラーは待って再試行誤りはゼロにならない前提で、行き先を決めておく
安全個人情報を伏せてから送る。本文はログに残さない制約「本文を社外のログに残さない」
観測分類の結果・処理時間・費用・エラーを記録する⑧で品質と費用を見張るため

構成の選び方は エージェントとワークフロー、モデルの選び方は モデル選択と最適化、安全の仕組みは セキュリティと安全 で詳しく扱っています。

「いきなり自律的なエージェントにする」より「要件を満たすいちばん単純な構成」が正解になりやすい。確実にしたい処理（形の確認、個人情報の除去）はモデルに頼らずコードで行う。

④ 評価の準備：合格の基準とデータを先に作る

作り始める前に、「何ができたら合格か（成功基準）」と、それを測るための評価データを用意します。Anthropic のドキュメントも、まず成功基準を決め、それを測るテストを作ってから、プロンプトの改善に進む順番で説明しています。

  • 成功基準：②の要件をそのまま使います。「評価データ300件で正答率95%以上」「1件5秒以内」「1件3円以下」。
  • 評価データ：ディスカバリーで見つけた「過去1年分の振り分け結果」から300件を選び、個人情報を伏せて使います。よくあるメールだけでなく、返品と苦情の区別が難しいメールや空のメールも入れます。

評価データの形、採点の方法、結果の読み方は 評価（eval）とは何か で詳しく説明しています。

⑤ 実装・プロンプト：作って、評価で磨く

コードとプロンプトを書きます。最初から完璧なプロンプトは書けないので、書く → 評価する → 間違えた例を読む → 直すを、成功基準を満たすまで繰り返します。

例えば1回目の評価で「返品と苦情の区別が苦手」と分かったら、プロンプトに区別の基準と例を足して、もう一度評価します。このとき、一度に1か所だけ変えると、どの変更が効いたかが分かります。プロンプトはコードと同じように版で管理し、どの版で何点だったかを残します。

プロンプトの書き方は プロンプトとコンテキスト、API の使い方は Messages API で扱っています。

⑥ テスト：部品と全体が正しく動くか

評価が「LLM の出力の質」を測るのに対して、テストはプログラムが決めたとおりに動くかを確かめます。小さい単位から順に確かめます。

テスト例のアプリで確かめること
単体テスト前処理の関数が署名を除き、電話番号を伏せるか。検証の関数が「5種類以外」をはじくか。Claude の応答は決まった答えを返す偽物（モック）に置き換える
結合テスト受付システムから届いたメールが、前処理 → 分類 → キューまで正しく渡るか
E2E テストテスト用のメールを1通送り、担当の窓口の画面に表示されるまでを通して確かめる

テストは「毎回同じ結果」を期待するので、出力がぶれる LLM の部分はモックに置き換えるか、評価のほうで割合を測ります。用語は 用語集のテストの種類 にあります。

⑦ デプロイメント：少しずつ本番に出す

評価とテストに合格したら、本番で利用者に使ってもらいます。いきなり全員に出すのではなく、一部から始めて、問題がなければ広げます。

  • カナリアリリース：図のように、一部の利用者から出して広げていく方法。問題が起きても影響が小さく済みます。
  • ロールバック（切り戻し）：問題が起きたら前の版に戻すこと。出す前に、戻す手順を用意しておきます。プロンプトやモデルの設定を1か所で切り替えられるようにしておくと、すぐに戻せます。

「デプロイメント」という言葉の意味の広さは 用語集のデプロイメント で説明しています。

⑧ 運用・改善：見張って、直し続ける

本番に出したら終わりではありません。LLM のアプリは、コードを1行も変えなくても品質が変わることがあります。利用者の書き方が変わる、新しい種類の問い合わせが増える、モデルが更新される、といった理由です。

運用ですること例のアプリでは
監視「その他」に入る割合、人の確認に回る件数、処理時間、1日の費用を毎日見る。担当者が窓口を付け替えた件数を「誤りの数」として数える
改善付け替えられたメールを評価データに足し、プロンプトを直して評価し、少しずつ出す
モデルの更新への備え使うモデルの版を固定しておく。提供終了が告知されたら、新しいモデルを評価データで比べてから移行する
大きな変化「定期便」という新しい窓口ができた → 分類の種類が変わるので、①②から考え直す

監視に使う用語（インストルメンテーション、オブザーバビリティ、テレメトリ）は 用語集の運用と観測、ライフサイクルの要点は アプリケーションと統合「システムのライフサイクル」 にあります。

「エラーは出ていないのに、品質が下がった」→ エラー率の監視だけでは気づけない。出力の質を継続して見張り、失敗例を評価データに足す。「モデルが更新されて挙動が変わった」→ 版の固定と、評価してからの切り替え。

8つの段階をつなぐ1本の糸

8つの段階はばらばらではありません。①で決めた成功の指標が、形を変えながら最後まで使われます。

最初に成功の指標を決めておかないと、要件も、評価の基準も、リリースの判定も、監視で見る数字も決まりません。ディスカバリーが最初に来る理由はここにあります。

各段階で作るもの

段階答える問い作るもの（成果物）
① ディスカバリー誰が、何に、どれくらい困っている？課題の整理メモ、関係者の一覧、成功の指標
② 要件定義何を、どこまでできれば合格？機能要件・非機能要件の一覧（数字つき）
③ 設計どんな仕組みで実現する？構成図、モデルの選定理由、失敗時の扱い、設計の判断の記録
④ 評価の準備合格をどう測る？成功基準、評価データ、採点の方法
⑤ 実装・プロンプト作ったものは基準を満たす？コード、版を管理したプロンプト、評価の結果
⑥ テストプログラムは決めたとおりに動く？単体・結合・E2E のテスト
⑦ デプロイメント安全に本番に出せる？リリースの計画（段階と判定の基準）、切り戻しの手順
⑧ 運用・改善本番で品質を保てている？監視の画面と通知、改善の記録、更新した評価データ

よくある間違い

よくある間違い何が困るか正しくは
依頼された機能をそのまま作り始める本当の課題とずれ、作り直しになる①で課題と成功の指標を確かめてから
要件が「速く」「正確に」だけ完成したかどうか判定できない②で数字にする（5秒以内、95%以上）
最初から自律的なエージェントにする遅く、高く、予測しにくい③で要件を満たすいちばん単純な構成を選ぶ
何回か試して良さそうなので出す出力のぶれや一部の入力での失敗に気づけない④⑤で評価データを使って数字で判定する
いきなり全員に出す問題が起きると全員に影響する⑦で一部から出し、戻す手順を用意する
出したら終わり品質の低下やモデルの更新に気づけない⑧で見張り、失敗を評価データに戻す

この章のまとめ

  • 開発は ①ディスカバリー → ②要件定義 → ③設計 → ④評価の準備 → ⑤実装 → ⑥テスト → ⑦デプロイメント → ⑧運用・改善 の流れ。⑧から④⑤（大きな変化なら①）に戻る輪になっている。
  • ディスカバリーは「本当の課題」を見つける段階。依頼は解決策の形で来るので、「なぜ？」で掘り下げる。成功の指標とデータを必ず確かめる。
  • 要件は数字で測れる形に。それがそのまま評価の成功基準になる。
  • 設計は、要件を満たすいちばん単純な構成から。確実にしたい処理はコードで。
  • 評価の準備は実装より先。作ったら評価で磨き、合格したら一部から本番に出す。
  • LLM のアプリはコードを変えなくても品質が変わる。出した後も見張って直し続ける。
