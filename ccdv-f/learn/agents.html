エージェントとワークフロー 配点 14.7%

いつエージェントを使い、いつワークフローにするか。エージェントをどう作り、どう安全に止めるか。代表的なパターンとフレームワークまでを扱います。

この章の前提：はじめに（前提知識）の ツール利用とエージェントの考え方・プログラムの読み方・サーバーはどこにある？

ワークフローか、エージェントか

観点ワークフローエージェント
手順事前に決まっている入力ごとに変わる・探索が必要
予測しやすさ・テスト高い低い（ばらつく）
費用・時間小さく一定大きく、ばらつく
例請求書の抽出 → 検算 → 登録障害の原因調査、コードベースの修正

原則は「最も単純な方法から」。1回の呼び出し（検索やツール付き）で足りるならそれで、決まった手順ならワークフロー、手順を決められないときにエージェントを選びます。

マネージャー／スーパーバイザーとサブエージェント

  • 親（マネージャー）は計画と統合を担い、子（サブエージェント）は独自のコンテキストで作業する。
  • 大量の途中経過が親に溜まらないので、コンテキストの肥大化を防げる。並列化もできる。
  • 子からの返却は、結論・根拠・出典などの決まった形式の要約にする。

Claude でエージェントを作る

Claude Agent SDK

Claude Code を支える仕組み（エージェントのループ、組み込みツール、コンテキスト管理、権限、フック、サブエージェント、MCP 連携など）を、部品として自分のアプリで使えるようにしたものです。一から作る手間を省き、独自の機能はカスタムツールやフックで足します。

独自のエージェントループ

while 繰り返し回数 < 上限:
    res = Messages API を呼ぶ（tools つき、履歴つき）
    if res.stop_reason != "tool_use": break        # 最終回答
    履歴に res.content（assistant）を追加
    結果 = 各 tool_use を実行（失敗は is_error: true）
    履歴に tool_result（user）を追加
else:
    上限に達した → 停止して状況を報告

細かい制御が必要なときは自分でループを書きます。その場合、停止条件（最大回数・トークンや時間の予算）、エラーを正直に返すこと、記録（トレース）を必ず入れます。

フックで「必ず」行う

フックは、ツールの実行前後などの決まったタイミングで、モデルの判断と関係なく必ず実行される処理です。

タイミング（例）使い方
ツールの実行前（PreToolUse）危険なコマンドをブロック、入力の検査
ツールの実行後（PostToolUse）編集後に必ずフォーマッターやテストを実行、記録
セッションの開始・終了など文脈の読み込み、通知、後片付け
「必ず」「確実に」「忘れてはならない」→ プロンプトの指示ではなくフック（決定的な仕組み）。

デプロイの方式

セルフホスト

  • 自社の環境で実行
  • 内部ネットワークやデータに直結
  • 実行環境・ログを自社で管理

Anthropic がホスト

  • 実行環境の運用を任せられる
  • 素早く始められる
  • 内部システムとの接続方法は要確認

代表的なパターン

ワークフローには、よく使われる5つの型（パターン）があります。どれも「LLM を何回、どの順番で、どうつないで呼ぶか」をコードで決めておく作り方です。型を知っておくと、業務を見たときに「これはルーティングで振り分けて、その先はチェーンにしよう」のように、組み立て方をすぐに考えられます。

LLM の呼び出し
Messages API にリクエストを1回送り、返答を1つ受け取ること。この節の図では青い箱で表します。
コード（プログラム）
Python などで書いた、毎回同じように動く処理。条件の判定や結果の集計など、LLM に任せなくてよい部分です。図ではオレンジの箱で表します。
ゲート
途中で結果を確かめ、次へ進むか止めるかを決める関門。件数や形式など、確かめられることはコードで判定します。
集約
複数の結果を1つにまとめること。並べる、多数決をとる、LLM に統合させる、などの方法があります。
同時に実行（並行処理）
1つ目の返事を待たずに2つ目・3つ目の呼び出しを送り、まとめて待つこと。Python では asyncio.gather を使います（アプリケーションと統合で扱います）。

サンプル：この節のコードで使う、共通の部品

import json
import anthropic

client = anthropic.Anthropic()

def ask(prompt, model="claude-sonnet-5-5"):
    """Claude に1回だけ質問して、返答の文章を返す（＝図の青い箱1つ）"""
    res = client.messages.create(
        model=model,
        max_tokens=1024,
        messages=[{"role": "user", "content": prompt}],
    )
    return res.content[0].text

以下のサンプルでは、ask(...) が1回出てくるたびに、LLM を1回呼んでいます。ask が何回、どの順番で呼ばれるかに注目すると、パターンの違いが見えてきます。

① プロンプトチェーン：決まった順に1本道で進む

一言でいうと：大きな仕事を順番のある小さな仕事に分け、前の出力を次の入力にして、LLM を順に呼びます。工場のベルトコンベアのように、各工程は自分の仕事だけをします。

例：通販サイトの商品ページを作る。商品データから特徴を抜き出し、説明文を書き、英語に翻訳する。

サンプル：商品ページを3段階で作る

def write_product_page(product):
    # ① 抽出：売りになる特徴を3つ抜き出す（LLM）
    features = ask(f"次の商品データから、購入の決め手になる特徴を3つ、1行に1つずつ書いてください。\n{product}")

    # ゲート：次に進んでよいかを、コードで確かめる
    lines = [l for l in features.splitlines() if l.strip()]
    if len(lines) != 3:
        raise ValueError("特徴が3つ取れなかったので、ここで止める")

    # ② 執筆：特徴をもとに説明文を書く（LLM）
    draft = ask(f"次の特徴をもとに、200字の商品説明を書いてください。\n{features}")

    # ③ 翻訳：英語版を作る（LLM）
    return ask(f"次の文章を自然な英語に翻訳してください。\n{draft}")

ask は必ず3回、必ずこの順番で呼ばれます。どの商品でも流れは同じです。

なぜ分けるのか：「特徴を抜き出して、説明文を書いて、英訳して」を1回で頼むと、どこで失敗したのかが分からず、直すのも難しくなります。分けると次の利点があります。

  • 各プロンプトが短く具体的になり、1つの仕事に集中できるので精度が上がる。
  • 途中の出力をゲートで確かめられる。おかしければ、後の工程に進む前に止められる。
  • 工程ごとにテストでき、工程ごとにモデルを変えられる（例：翻訳だけ安いモデルにする）。

代わりに、呼び出しの回数が増えるので、全体の時間は長くなります。速さよりも確実さを取る作り方です。

向いている

  • 手順が毎回同じで、順番に意味がある
  • 途中で確かめたい点がある（件数・形式・必須項目）
  • 例：抽出 → 検証 → 登録、下書き → 校正 → 翻訳

向いていない

  • 入力によって必要な手順が変わる（→ ルーティングかエージェント）
  • 応答の速さが最優先（工程の数だけ待ち時間が増える）
問題文の手がかり：「決まった手順」「段階ごとに検証したい」「1つのプロンプトに詰め込みすぎて精度が出ない」→ プロンプトチェーン。

② ルーティング：種類を見て、1つの道に振り分ける

一言でいうと：最初に入力の種類を判定し、その種類に合った専用の処理に送ります。総合受付が、用件を聞いて担当の窓口を案内するのと同じです。

例：問い合わせ窓口。返品、技術的な質問、よくある質問が混ざって届く。

サンプル：問い合わせを種類ごとに振り分ける

ROUTES = {
    "返品": {"model": "claude-haiku-5-5",  "prompt": "返品規程に沿って答えてください。規程：…"},
    "技術": {"model": "claude-sonnet-5-5", "prompt": "製品マニュアルをもとに、手順を順番に説明してください。…"},
    "FAQ":  {"model": "claude-haiku-5-5",  "prompt": "よくある質問の一覧から答えてください。一覧：…"},
}

def handle(question):
    # 振り分け：種類だけを答えさせる（判定だけなので、安くて速いモデルで十分）
    label = ask(
        f"次の問い合わせを「返品」「技術」「FAQ」「その他」のどれか1語で分類してください。\n{question}",
        model="claude-haiku-5-5",
    ).strip()

    if label not in ROUTES:              # 「その他」や、想定外の答えが返ってきた
        return send_to_human(question)   # 人の担当者に回す

    route = ROUTES[label]
    return ask(route["prompt"] + "\n問い合わせ：" + question, model=route["model"])

ask は、判定で1回と、選ばれた担当で1回の合計2回です。選ばれなかった担当のプロンプトは一度も使われません。

なぜ分けるのか：1つのプロンプトに「返品ならこう、技術ならこう、FAQ ならこう」と全部書くと、プロンプトが長くなり、ある種類のために直した指示が別の種類の回答を悪くすることがあります。振り分ければ、次のことができます。

  • 担当ごとに、専用のプロンプト・ツール・モデルを用意できる。
  • 簡単な問い合わせは安いモデル、難しいものは高性能なモデルに回して、費用を抑えられる（モデルのルーティング）。
  • 1つの担当を直しても、ほかの担当に影響しない。

注意点は、振り分けを間違えると、その先がどれだけ優秀でも正しく答えられないことです。判定の正確さを評価で確かめ、判定できないものの行き先（人に回すなど）を必ず決めておきます。分類の答えは、構造化出力で選択肢（enum）に限定すると、想定外の文字列を防げます。

向いている

  • 性質の違う入力が混ざって届く
  • 種類ごとに最適な処理やモデルが違う
  • 種類を正確に判定できる

向いていない

  • 種類の境目があいまいで、判定がぶれる
  • 1つの入力に複数の処理を全部かけたい（→ 並列化）
問題文の手がかり：「種類の異なる問い合わせ」「簡単なものは安いモデルで」「カテゴリごとに専用の対応」→ ルーティング。

③ 並列化：同時に呼んで、あとでまとめる

一言でいうと：互いに関係しない複数の呼び出しを同時に行い、結果をコードでまとめます。使い方が2種類あります。

種類何を同時に行うか得られるもの例
A. 分割（セクショニング）1つの仕事を独立した部分に分け、部分ごとに呼ぶ速さ。各呼び出しが1つの観点に集中できる契約書を観点ごとに確認する／回答の作成と、不適切な内容の検査を同時に行う
B. 投票（ボーティング）同じ仕事を複数回呼ぶ判断の安定。1回だけの見落としや思い込みを減らす脆弱性の検査を3回行い、多数決で判定する

サンプル：分割と投票（非同期で同時に呼ぶ）

import asyncio
from anthropic import AsyncAnthropic

aclient = AsyncAnthropic()

async def aask(prompt):
    res = await aclient.messages.create(
        model="claude-sonnet-5-5", max_tokens=1024,
        messages=[{"role": "user", "content": prompt}],
    )
    return res.content[0].text

# A. 分割：観点ごとに別の呼び出しにして、同時に確認する
async def review_contract(text):
    points = ["支払条件", "解約条項", "責任の範囲"]
    results = await asyncio.gather(*[
        aask(f"次の契約書の「{p}」だけを確認し、問題点を挙げてください。\n{text}")
        for p in points
    ])
    return dict(zip(points, results))        # まとめるのはコード

# B. 投票：同じ検査を3回行い、2回以上「あり」なら要確認にする
async def is_risky(code):
    answers = await asyncio.gather(*[
        aask(f"次のプログラムに安全上の問題があれば「あり」、なければ「なし」とだけ答えてください。\n{code}")
        for _ in range(3)
    ])
    return sum(a.strip() == "あり" for a in answers) >= 2

asyncio.gather で3つの呼び出しを同時に送ります。順番に呼ぶと3回分待ちますが、同時ならいちばん遅い1回分の待ち時間で済みます。呼び出しの回数は3回のままなので、料金は減りません。

大事な条件は、同時に行う仕事が互いの結果を必要としないことです。「支払条件の結果を見てから解約条項を判断する」ような依存があるなら、同時にはできません（→ チェーン）。また、分け方（観点の一覧や回数）はコードに書いてあり、実行前から決まっています。ここが次のオーケストレーター／ワーカーとの違いです。

向いている

  • 独立した観点・部分に分けられる
  • 待ち時間を短くしたい
  • 見落としが許されない判定を安定させたい（投票）

向いていない

  • 前の結果を見ないと次が決まらない
  • 課題ごとに分け方が変わる（→ オーケストレーター／ワーカー）
  • 費用を下げたい（呼び出しの回数は減らない）
問題文の手がかり：「独立した観点」「待ち時間を短く」「複数回の判定で信頼性を上げる」「回答とガードレールを同時に」→ 並列化。

④ オーケストレーター／ワーカー：分け方を LLM が決める

一言でいうと：司令役の LLM（オーケストレーター）が課題を読んで「何をいくつに分けるか」を考え、作業役の LLM（ワーカー）にそれぞれを任せ、最後に結果を統合します。現場監督が、工事の内容を見てから職人に仕事を割り振るのに似ています。

例：「会員登録に電話番号の欄を追加して」という依頼。画面、API、データベース、テストのどれを直す必要があるかは、依頼の内容とコードを見るまで分かりません。別の依頼なら、直す場所も数もまったく違います。

サンプル：依頼を分けて、ワーカーに任せ、統合する

def build_feature(request):
    # ① 計画：何をいくつに分けるかを LLM に決めさせる（JSON で受け取る）
    plan = json.loads(ask(
        "次の依頼を、独立して進められる作業に分けてください。"
        '[{"task": "作業内容", "files": ["対象ファイル"]}] の形の JSON だけを返してください。\n'
        + request
    ))
    plan = plan[:5]          # 安全のため、ワーカーの数に上限をかける

    # ② 実行：作業ごとにワーカーを呼ぶ（いくつになるかは、①の結果しだい）
    results = [
        ask(f"次の作業だけを行い、変更内容を3行で要約して返してください。\n{json.dumps(t, ensure_ascii=False)}")
        for t in plan
    ]

    # ③ 統合：結果をまとめ、作業どうしの食い違いがないか確かめる
    return ask("次の作業結果を1つにまとめ、矛盾があれば指摘してください。\n" + "\n---\n".join(results))

③並列化のサンプルでは、観点の一覧 ["支払条件", "解約条項", "責任の範囲"] がコードに書いてありました。ここでは plan がLLM の返答から作られます。この1点が2つのパターンの違いです。ワーカーどうしが独立していれば、②は並列化と同じく同時に実行できます。

設計のポイント：

  • ワーカーには自分の作業に必要な情報だけを渡し、結果は決まった形式の短い要約で返させる。統合役のコンテキストがあふれるのを防げる（サブエージェントと同じ考え方）。
  • LLM が分け方を決めるので、ワーカーが想定以上に増えることがある。数・費用・時間の上限をコードでかける。
  • 計画（plan）を記録しておくと、なぜその結果になったかを後から追える。

向いている

  • 課題ごとに、必要な作業の数や中身が変わる
  • 分けた作業は互いに独立して進められる
  • 例：複数ファイルにまたがるコード修正、複数の情報源を調べるリサーチ

向いていない

  • 分け方が毎回同じ（→ 並列化のほうが安く、予測しやすい）
  • 作業どうしが密に依存し、こまめなやり取りが必要

エージェントとの関係：オーケストレーター／ワーカーは「計画 → 実行 → 統合」という大枠はコードで決まっていて、LLM が決めるのは分け方だけです。エージェントは、次に何をするかを毎回 LLM が決め、ゴールまで繰り返します。オーケストレーター役やワーカー役をエージェントにする作り方もあり、前の節のマネージャーとサブエージェントがその例です。

問題文の手がかり：「事前にサブタスクを決められない」「課題によって作業の数が変わる」「複数ファイルの変更」→ オーケストレーター／ワーカー。分け方が固定なら並列化。

⑤ 評価者／改善者：合格するまで直させる

一言でいうと：生成役の LLM が下書きを作り、評価役の LLM が基準に照らして採点します。不合格なら、直すべき点（フィードバック）を生成役に返して作り直させます。書き手と編集者が、原稿をやり取りして仕上げていくのと同じです。

例：広告の基準を守った商品説明文を作る。「200字以内」「誇大な表現を使わない」「価格を書かない」という基準がある。

サンプル：基準を満たすまで直させる（最大3回）

CRITERIA = "・200字以内　・「必ず」「最高」などの誇大な表現を使わない　・価格を書かない"

def write_with_review(product, max_rounds=3):
    draft = ask(f"次の商品の説明文を書いてください。\n{product}")          # 生成役

    for _ in range(max_rounds):
        if len(draft) > 200:                     # 数えられる基準は、コードで判定する
            feedback = f"{len(draft)}字あります。200字以内にしてください。"
        else:
            review = json.loads(ask(                                     # 評価役
                f"次の説明文が基準を満たすか評価してください。\n基準：{CRITERIA}\n説明文：{draft}\n"
                '{"pass": true または false, "feedback": "直すべき点"} の形の JSON だけを返してください。'
            ))
            if review["pass"]:
                return draft                     # 合格したら終わり
            feedback = review["feedback"]

        draft = ask(f"次の指摘に従って説明文を直してください。\n指摘：{feedback}\n説明文：{draft}")  # 生成役

    return send_to_human(draft)                  # 上限まで直しても合格しない → 人に回す

ask の回数は、1回目で合格すれば2回、3回直せば最大で7回です。入力によって回数が変わるので、必ず上限（max_rounds）を決めておきます。

うまく働く条件は2つです。

  1. 評価の基準がはっきりしている。「良い文章か」では評価がぶれて、いつまでも合格しなかったり、何でも合格になったりします。「200字以内」「この語を使わない」のように判定できる形にします。
  2. 指摘をもらえば、実際に良くなる仕事であること。人が赤ペンを入れると良くなる翻訳や文章、コードは向いています。

字数のようにコードで確かめられる基準は、LLM に採点させずにコードで判定します（サンプルの len(draft)）。そのほうが速く、安く、毎回同じ結果になります。評価役は生成役と別の呼び出し・別のプロンプトにします。同じ会話の中で「自分の文章を見直して」と頼むより、自分の出力に甘くなりにくいためです。

向いている

  • 評価の基準を言葉や数値ではっきり書ける
  • 指摘を受けて直すと、質が上がる
  • 例：基準つきの文章作成、翻訳の仕上げ、テストが通るまでのコード修正

向いていない

  • 基準があいまい（「いい感じに」）
  • 1回目の品質で十分（繰り返すほど費用と時間がかかる）
  • 上限を決めずに回す（終わらない・費用が膨らむ）
問題文の手がかり：「明確な評価基準がある」「反復して品質を上げたい」「自己チェックでは見落とす」→ 評価者／改善者。必ず回数の上限とセットで考える。

5つのパターンの見分け方

迷ったときは、「道は何本か」「分け方を決めるのは誰か」「繰り返すか」の3点を確かめます。

パターン流れの形分け方・道を決めるのは繰り返し主に得るもの
① チェーン1本道を順に進むコード（固定）なし精度、途中での検証
② ルーティング分かれ道から1本だけ選ぶ振り分け役（LLM かルール）なし専用の処理、費用の削減
③ 並列化複数の道を全部同時に進み、合流コード（固定）なし速さ、判断の安定
④ オーケストレーター／ワーカー複数の道を進み、合流LLM が実行時に決めるなし決められない分け方への対応
⑤ 評価者／改善者作る → 採点 → 直す の輪コード（固定）あり（上限つき）品質の向上

特に間違えやすい組み合わせです。

組み合わせ違い
② ルーティング と ③ 並列化（分割）ルーティングは1本だけ実行し、残りは使わない。並列化は全部実行して結果をまとめる
③ 並列化 と ④ オーケストレーター／ワーカー分け方がコードに書いてあって固定なら並列化。LLM が課題を見て決めるならオーケストレーター／ワーカー
① チェーン と ⑤ 評価者／改善者チェーンは前に進むだけで戻らない。評価者／改善者は不合格なら戻って直す輪がある
④ オーケストレーター／ワーカー と エージェント④は「計画 → 実行 → 統合」の枠が決まっている。エージェントは次の一手を毎回 LLM が決め、何回繰り返すかも決まっていない

組み合わせて使うのが普通です。例えば問い合わせ窓口なら、ルーティングで種類を分け、「返品」の道の中はチェーン（規程の検索 → 回答の作成 → 個人情報の検査）にし、最後の回答を評価者でチェックする、という形になります。どの場合も、原則は変わりません。いちばん単純な作り方で足りるならそれを選び、必要なときだけパターンを足します。

メモリとコンテキストの管理

  • 長い作業は、進捗や決定事項をファイルなどの外部メモリに書き出し、次のセッションで読み込む。
  • コンテキストが膨らんだら、要約して圧縮する（コンパクション）、古いツール出力を削る。
  • 重い調査はサブエージェントに分ける。

フレームワーク

LangGraph、Strands、PydanticAI などのフレームワークは、状態の管理・分岐・再試行・可視化などの骨組みを提供します。

利点

  • 多段の処理を速く組める
  • 流れを図やグラフで共有しやすい

注意点

  • 抽象化の内側で送られるプロンプトが見えにくい
  • 品質は評価で確かめる必要がある
  • 料金は変わらない

この分野のまとめ

  • 単純な方法から。決まった手順はワークフロー、探索が必要ならエージェント。
  • サブエージェントでコンテキストを分離。返却は要約で。
  • ループには停止条件。「必ず」の処理はフック。
  • パターン：チェーン（1本道）・ルーティング（1本だけ選ぶ）・並列化（全部同時に、分け方は固定）・オーケストレーター／ワーカー（分け方を LLM が決める）・評価者／改善者（合格まで直す、上限つき）。
