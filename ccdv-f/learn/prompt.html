プロンプトとコンテキスト 配点 11.0%

プロンプトの書き方、コンテキスト（モデルに渡す情報全体）の管理、出力の扱い方を学びます。「何を、どこに、どれだけ渡すか」がテーマです。

この章の前提：はじめに（前提知識）の コンテキスト・JSON Schema・LLM の基本

プロンプトエンジニアリング

基本の原則

原則具体的には
明確に・具体的に目的、読み手、形式、長さ、制約を書く。「良い感じに」ではなく基準を示す
例を示す（few-shot）典型例と境界例を、偏りなく。例は <example> タグで囲む
指示とデータを分ける資料は <document> などのタグで囲み、データであることを明記
置き場所方針・役割は system、その回の依頼とデータは user。長い資料は先、質問は後ろ
出力の制約形式（JSON・見出し）、長さ、言語を指定。機械が読むなら構造化出力
考えさせる複雑な推論は段階的に考えさせる（思考の機能も活用）
繰り返し改善評価データで効果を測り、1回に1つずつ変える

system と user の使い分け

"system": "あなたは社内ヘルプデスクの担当です。丁寧語で、社外秘の情報は答えません。",
"messages": [{"role": "user", "content": [
  {"type": "text", "text": "<document>…社内 FAQ…</document>"},
  {"type": "text", "text": "VPN に接続できません。どうすればいいですか？"}
]}]

入力のサニタイズ

利用者の入力をプロンプトに埋め込む前に、区切りに使うタグと同じ文字列の除去やエスケープ、長さの制限などを行います。悪意がなくても、偶然プロンプトの構造が崩れることがあります。

few-shot の例に偏りがあると出力も偏る。「例を増やす」ではなく「多様でバランスよく」。

コンテキストエンジニアリング

コンテキストとは、1回の呼び出しでモデルに渡す情報の全体（system、ツール定義、履歴、資料、ツールの出力）です。「たくさん入れる」より「必要なものを選ぶ」が原則です。

問題症状対策
肥大化（bloat）遅い、高い、重要な情報が埋もれる不要なツール出力の削除（pruning）、要約による圧縮（compaction）
ドリフト（drift）長い会話で、最初の指示や目的から外れていく重要な指示を system に置く、要約時に目的を引き継ぐ、セッションを分ける
混線無関係な話題や他のタスクが混ざるサブエージェントや多段のワークフローでコンテキストを分離

出力の扱い

構造化出力と検証

  1. 形を決める：構造化出力（output_config.format）や strict なツール。
  2. 検証する：スキーマ、業務上の値の範囲、参照の整合性。
  3. 失敗に備える：理由を添えて再生成、既定の安全な処理、人への引き継ぎ。

自信のある出力を疑う

LLM は、根拠がなくても自信のある書き方で答えることがあります（ハルシネーション）。

  • 根拠（資料の引用）を示させる。引用が資料に実在するかをアプリで確認できる。
  • 「分からない」と答えてよいことを明示する。
  • 重要な値（金額・日付・条番号）は、元のデータと照合する。

この分野のまとめ

  • 明確に、例はバランスよく、指示とデータはタグで分ける。
  • 方針は system、データと依頼は user。入力はサニタイズ。
  • コンテキストは選ぶ：pruning・compaction・分離。
  • 出力は形を決めて検証。自信のある出力ほど根拠を確かめる。
